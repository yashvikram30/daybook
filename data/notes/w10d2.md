# Partitioning (sharding)

Split data across nodes when it exceeds one machine's storage or throughput. Each key belongs to one **partition**; each partition is itself replicated.

| Scheme          | Pros                        | Cons                                         |
| --------------- | --------------------------- | -------------------------------------------- |
| **Key range**   | range scans, ordered        | **hot spots** (sequential keys / timestamps) |
| **Hash** of key | even spread                 | no range queries (scatter-gather)            |
| Compound        | hash prefix + sorted suffix | more design                                  |

Also: **skew/hot keys** (celebrity users) need special handling; **secondary indexes** are either local (query all partitions) or global.

# Why `hash(key) % N` is bad

Changing N (add/remove a node) changes the mapping for almost every key: **~(N−1)/N of keys move**, causing a storm of data movement and cache misses.

# Consistent hashing

Hash both **nodes** and **keys** onto a ring (e.g. 0 … 2³²−1). A key is owned by the **first node clockwise** from its hash.

```
        n1
     ╱      ╲        key k → next node clockwise (n2)
   n3         n2 ◄── k
     ╲      ╱
        ...
```

Adding/removing a node moves only the keys between it and its neighbor: **≈ 1/N of keys**.

**Virtual nodes:** each physical node gets many (e.g. 100-256) points on the ring. This **evens out load** (with one point per node, arcs are uneven), spreads a failed node's load across many peers, and lets stronger machines take more points. **Replication:** store each key on the next R distinct nodes clockwise (Dynamo's preference list).

```python
import bisect, hashlib

def h(key: str) -> int:
    return int.from_bytes(hashlib.md5(key.encode()).digest()[:4], "big")     # stable across processes

class Ring:
    def __init__(self) -> None:
        self.hashes: list[int] = []
        self.owner: dict[int, str] = {}

    def get(self, key: str) -> str:
        i = bisect.bisect_left(self.hashes, h(key))
        if i == len(self.hashes):
            i = 0                                         # wrap around
        return self.owner[self.hashes[i]]
```

Do not use Python's built-in `hash()` for the ring: string hashing is randomised per process, so two nodes would disagree about who owns a key.

Alternatives: **rendezvous (HRW) hashing**, **jump consistent hash**, fixed number of partitions assigned to nodes (Kafka, Elasticsearch, Redis Cluster's 16384 slots).

# Ring with virtual nodes

```python
def add(self, node: str, vnodes: int) -> None:
    for i in range(vnodes):
        p = h(f"{node}#{i}")
        self.owner[p] = node
        bisect.insort(self.hashes, p)
```

Use a hash with good avalanche behaviour (`hashlib` is fine here; `xxhash`/`mmh3` are faster third-party choices); never something weak like summing the bytes. Remove: delete the node's points.

# Experiments

1. **Distribution:** 100k random keys over 10 nodes with 1, 10, 100 vnodes; report per-node counts, **max/mean** and standard deviation. Expect 1 vnode to be badly skewed, 100 within ~10%.
2. **Churn:** add an 11th node; fraction of keys whose owner changed ≈ **1/11 ≈ 9%** (vs ~91% with `% N`). Remove a node; only its keys move.
3. Test determinism, wrap-around, and that every key has exactly one owner.

# Counting, flattening, building

**Count nodes of a complete tree in O(log² n):** compute the leftmost-depth and rightmost-depth; if equal the subtree is perfect → `2^h − 1`; else recurse on both children.

```python
def count(n: TreeNode | None) -> int:
    if n is None:
        return 0
    lh = rh = 0
    x = n
    while x:
        lh += 1
        x = x.left
    x = n
    while x:
        rh += 1
        x = x.right
    if lh == rh:
        return (1 << lh) - 1
    return 1 + count(n.left) + count(n.right)
```

**Flatten to a linked list (preorder, in place):** reverse-postorder with a `prev` pointer: `visit right, then left; node.right = prev; node.left = None; prev = node`.

**Which traversals give a unique tree?** Inorder + preorder, or inorder + postorder: **yes**. Preorder + postorder: **no** (ambiguous when a node has one child). Inorder is always needed.

**Build from preorder + inorder:** the first preorder element is the root; find it in inorder (use a **map value → index** for O(1)) to split left/right sizes.

```python
def build(pre: list[int], inorder: list[int]) -> TreeNode | None:
    if not pre:
        return None
    i = inorder.index(pre[0])                 # use a dict value -> index for O(n) total
    return TreeNode(pre[0], build(pre[1:i + 1], inorder[:i]), build(pre[i + 1:], inorder[i + 1:]))
```

Postorder + inorder: the **last** postorder element is the root.

# Capacity thinking

Estimate before you build: **order of magnitude is enough**.

| Quantity               | Useful number                                                                          |
| ---------------------- | -------------------------------------------------------------------------------------- |
| seconds per day        | ~86,400 ≈ 10⁵                                                                          |
| QPS from per-day count | `requests/day ÷ 10⁵` (peak ≈ 2-5× average)                                             |
| memory read            | ~100 ns; SSD random read ~100 µs; same-datacenter RTT ~0.5 ms; cross-continent ~150 ms |
| powers of two          | 2¹⁰ ≈ 1 KB, 2²⁰ ≈ 1 MB, 2³⁰ ≈ 1 GB, 2⁴⁰ ≈ 1 TB                                         |

Example: 100 M users × 1 write/day → 10⁸/10⁵ = **~1,000 writes/s** average; at 1 KB each → ~1 MB/s, **~86 GB/day**, ~31 TB/year (×replicas). Then find the **bottleneck** (CPU, memory, disk IOPS, network) and ask what changes at 10×.
