# A framework for design questions (45 min)

1. **Requirements:** functional (what it does) and non-functional (scale, latency, availability, consistency, durability). Ask, don't assume.
2. **Estimates:** users, QPS (avg/peak), storage, bandwidth, read:write ratio.
3. **API:** the few endpoints and their semantics.
4. **Data model** and storage choice.
5. **High-level design:** clients → LB → services → cache → DB/queue.
6. **Deep dive** on 1-2 hard parts (hot keys, ID generation, rate limiting).
7. **Failure modes and bottlenecks**, then scaling.

# URL shortener (sketch)

- Requirements: create short URL, redirect, ~100 M new/month, read-heavy (100:1), links rarely change.
- Estimate: 100 M/month ≈ **40 writes/s**, ~4,000 reads/s; 500 B per record × 100 M × 5 yrs ≈ 3 TB.
- API: `POST /urls {long}` → `{short}`; `GET /{short}` → `301/302`.
- ID: base62 of a counter (7 chars ≈ 3.5 T ids) from a distributed ID generator / pre-allocated ranges, or hash + collision check.
- Store `short → long` in a key-value store sharded by short id (consistent hashing); **cache** hot redirects.
- Failures: ID collisions, hot link (cache + replicas), DB down (serve from cache), abuse (rate limit).

# Load balancing

A load balancer spreads requests over several servers for capacity and availability. **Layer 4** balancers route TCP connections; **layer 7** ones read HTTP and can route by path or header, terminate TLS, and retry.

| Algorithm            | Idea                                                | Notes                                                                                     |
| -------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Round robin          | rotate through the servers                          | simple; assumes equal servers and requests                                                |
| Weighted round robin | bigger servers get more turns                       | for mixed hardware                                                                        |
| Least connections    | send to the server with the fewest open connections | adapts to slow requests                                                                   |
| Hash (IP or key)     | the same client or key goes to the same server      | gives stickiness and cache hits; use consistent hashing so adding a server moves few keys |
| Power of two choices | pick two at random, send to the less loaded         | nearly as good as least-connections without global state                                  |

**Health checks** remove a failed server automatically. The balancer itself must not be a single point of failure, so it is replicated (DNS with several addresses, or a shared virtual IP).

# Rate limiter

| Algorithm                    | Idea                                                            | Notes                      |
| ---------------------------- | --------------------------------------------------------------- | -------------------------- |
| **Token bucket**             | bucket refills at rate r up to burst b; a request takes 1 token | allows bursts; most common |
| Leaky bucket                 | queue drains at fixed rate                                      | smooths output             |
| Fixed window counter         | count per minute                                                | boundary spikes (2× burst) |
| Sliding window (log/counter) | exact/approx rolling count                                      | more memory/CPU            |

Distributed: keep counters in a shared store (Redis `INCR` + TTL / Lua script for atomicity) or shard by user id; accept slight inaccuracy for speed; decide **fail-open vs fail-closed** if the limiter store is down.

# Jepsen-style test of your cluster

1. **Clients:** N asyncio tasks (or threads) issue `put/get/cas` on a few keys, recording each operation's `invoke` time, `complete` time and result into a **history** (`ok`, `fail`, or `info` = unknown after timeout).
2. **Nemesis:** random partitions, leader kills, message drops/delays, restarts.
3. **Check** small histories by hand (or write a brute-force checker for ≤ ~10 ops): is there an order of operations consistent with real-time order where every read returns the latest write? Mind `info` ops (they may or may not have happened).
4. Report violations, e.g. a stale read from a follower, a lost acknowledged write after failover.

# ADR

`Title: Replication = Raft with leader reads` · Status · Context · Decision · Consequences (linearizable reads via leader/read-index; follower reads rejected) · Alternatives considered.

# Binary search trees (BST)

Invariant: for every node, **left subtree < node < right subtree**. **Inorder gives sorted order.** Operations are O(h) (O(log n) if balanced, O(n) worst).

```python
def search(n: TreeNode | None, x: int) -> TreeNode | None:
    while n and n.val != x:
        n = n.left if x < n.val else n.right
    return n

def insert(n: TreeNode | None, x: int) -> TreeNode:
    if n is None:
        return TreeNode(x)
    if x < n.val:
        n.left = insert(n.left, x)
    else:
        n.right = insert(n.right, x)
    return n
```

**Delete:** no child → remove; one child → replace by the child; two children → replace the value with the **inorder successor** (min of right subtree) and delete that node.

```python
def delete(n: TreeNode | None, x: int) -> TreeNode | None:
    if n is None:
        return None
    if x < n.val:
        n.left = delete(n.left, x)
    elif x > n.val:
        n.right = delete(n.right, x)
    else:
        if n.left is None:
            return n.right
        if n.right is None:
            return n.left
        s = n.right
        while s.left:
            s = s.left
        n.val = s.val
        n.right = delete(n.right, s.val)
    return n
```

**Floor/ceil:** walk down; on `x ≥ val` record candidate floor and go right; else go left (ceil is symmetric).

**k-th smallest:** inorder traversal, stop at k (O(h + k)). k-th largest: reverse inorder (or `n−k+1`-th smallest).

# Estimation

Quick math that catches impossible designs early.

- Convert everything to **per second** (`÷ 10⁵` for per-day).
- Know the latency ladder (L1 ~1 ns, RAM ~100 ns, SSD ~100 µs, DC round trip ~0.5 ms, WAN ~100+ ms) and capacities (one commodity box: ~10k-50k simple req/s, ~1-10 TB disk, ~10 Gb/s network).
- Compute **storage** (items × size × replication × retention), **bandwidth** (QPS × payload), **memory for cache** (hot fraction, e.g. 20% of daily reads).
- Find the **first bottleneck** and state what you would change next. Say assumptions out loud; being within ~3× is fine.

1. **First bottleneck.** Depends on your design; typically the Raft **leader** (all writes and, if linearizable, reads go through it; fsync per commit) at ~10×, and **single-group storage/network** at ~100×, which is solved by sharding keys across multiple Raft groups. Reason numerically from your estimates.
2. **Leader + follower partitioned from the majority.** They are a minority: they can't commit new writes (no quorum), the leader steps down/stops serving linearizable requests when it can't reach a majority (check-quorum / lease), and the majority side elects a new leader. After healing, the minority's uncommitted entries are overwritten.
