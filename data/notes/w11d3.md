# API design principles (Bloch)

APIs outlive implementations and are hard to change. Be **easy to use, hard to misuse**; do one thing well; **minimize surface** (when in doubt, leave it out); use clear names and consistent conventions; document behavior; design for the common case.

# Resource-oriented HTTP APIs (Google guide)

- **Nouns**, not verbs: `/v1/keys/{key}`; standard methods: List `GET /keys`, Get `GET /keys/{k}`, Create `POST`, Update `PUT/PATCH`, Delete `DELETE`.
- **Version** in the path (`/v1`); **pagination** with an opaque cursor (`page_token`, `page_size`; offsets break under concurrent writes); consistent error format; idempotent updates.
- **Errors:** RFC 9457 **Problem Details**:

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json
{"type":"https://example.com/problems/key-not-found","title":"Key not found","status":404,"detail":"No key 'foo'","instance":"/v1/keys/foo"}
```

# OpenAPI sketch

```yaml
openapi: 3.0.3
info: { title: KV, version: 1.0.0 }
paths:
  /v1/keys/{key}:
    get:
      parameters: [{ name: key, in: path, required: true, schema: { type: string } }]
      responses:
        "200":
          {
            description: value,
            content: { application/json: { schema: { $ref: "#/components/schemas/Value" } } },
          }
        "404": { description: not found, content: { application/problem+json: {} } }
```

A spec lets you generate docs/clients and write **conformance tests** (server responses validate against the schema).

# REST vs gRPC

|               | REST/JSON               | gRPC                                     |
| ------------- | ----------------------- | ---------------------------------------- |
| Transport     | HTTP/1.1 or 2, text     | HTTP/2, binary protobuf                  |
| Contract      | OpenAPI (optional)      | `.proto` (required, codegen)             |
| Streaming     | limited (SSE/WebSocket) | native, bidirectional                    |
| Browsers      | native                  | needs gRPC-Web                           |
| Debuggability | `curl`, readable        | needs tooling                            |
| Fit           | public APIs             | internal service-to-service, low latency |

# Monolith vs microservices

Microservices give independent deploys/scaling and team autonomy, but cost **network failures, distributed data consistency, observability and operational overhead**. Fowler: **monolith first**; split when module boundaries are stable and a real need exists (team size, differing scaling/availability). A well-modularized monolith keeps the option open.

3. **Conformance test:** start the server on port 0 in a fixture, call each operation, validate status and body against the spec (e.g. with `openapi-core` or `schemathesis`) or hand-check required fields. If you build the service with **FastAPI**, the framework generates the OpenAPI document from your type hints and pydantic models (served at `/openapi.json`), so check that the generated spec matches the one you designed.
4. **ADR:** _REST vs gRPC for the KV service_: context (clients, browsers, performance), options, decision (REST for external API; revisit gRPC for node-to-node), consequences.

# Graph basics

Represent as an **adjacency list**: `adj = [[] for _ in range(n)]` (or `defaultdict(list)` keyed by name); matrix for dense graphs. Directed vs undirected (add both directions). **V** nodes, **E** edges.

| Traversal | Structure       | Gives                                          |
| --------- | --------------- | ---------------------------------------------- |
| **BFS**   | queue           | shortest path in **unweighted** graphs, levels |
| **DFS**   | recursion/stack | reachability, components, cycles, ordering     |

Both **O(V + E)**. Always keep a `visited` set to avoid infinite loops.

```python
from collections import deque

def bfs(adj: list[list[int]], s: int) -> list[bool]:
    seen = [False] * len(adj)
    seen[s] = True
    q = deque([s])
    while q:
        u = q.popleft()
        for v in adj[u]:
            if not seen[v]:
                seen[v] = True
                q.append(v)
    return seen
```

**Connected components / provinces:** for each unvisited node, traverse and `count++`.

**Islands (grid):** each `'1'` cell is a node with up to 4 neighbors; DFS marks the island visited (mutate `grid[r][c] = '0'` or use a seen array); count starts.

```python
DIRS = ((1, 0), (-1, 0), (0, 1), (0, -1))

def count_islands(g: list[list[str]]) -> int:
    m, n = len(g), len(g[0])

    def dfs(r: int, c: int) -> None:
        if r < 0 or c < 0 or r >= m or c >= n or g[r][c] != "1":
            return
        g[r][c] = "0"
        for dr, dc in DIRS:
            dfs(r + dr, c + dc)

    count = 0
    for r in range(m):
        for c in range(n):
            if g[r][c] == "1":
                count += 1
                dfs(r, c)
    return count
```

**Flood fill:** same, recolor cells that match the start color (stop if new color == old color).

Deep recursion on large grids: Python's default recursion limit (about 1000) will raise `RecursionError` on a big island, so prefer BFS or an explicit stack.

# Backward compatibility

Once clients exist, you can't just change an API.

| Breaking                                            | Safe (non-breaking)                                              |
| --------------------------------------------------- | ---------------------------------------------------------------- |
| remove/rename a field, endpoint or enum value       | add an **optional** field or new endpoint                        |
| change a type or meaning                            | add a new enum value _(only if clients tolerate unknown values)_ |
| make an optional input required; tighten validation | relax validation                                                 |
| change error codes or ordering guarantees           | add new error details                                            |

Clients should be **tolerant readers** (ignore unknown fields). **Rolling out a breaking change:** add the new behavior alongside the old (**expand**), announce deprecation (docs, `Deprecation`/`Sunset` headers), migrate clients, then remove (**contract**) in a new major version (`/v2`). Use feature flags and monitor old-version usage before deleting.

**Python packages:** the same rules apply to a library's public API: don't remove or rename public names (those in `__all__` or documented), change signatures or default values, or add abstract methods to a base class or `Protocol` that others implement (that breaks implementers). Adding functions, keyword arguments with defaults, or methods to a concrete class is fine. Breaking changes need a new major version; announce them first with `warnings.warn(..., DeprecationWarning)`.
