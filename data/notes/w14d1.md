# Treat the model as an unreliable component

Its output is **probabilistic text**. Your job is to make it predictable enough to build on: clear prompts, **constrained** output, **validation**, retries, logging.

# Prompting that works

- **Be clear and direct:** state the task, the audience/purpose, the constraints, the output format. Imagine briefing a smart new colleague with no context.
- **Examples (few-shot):** 3-5 diverse, realistic input → output pairs beat long descriptions for format and edge cases.
- **Separate instructions from data** with delimiters/XML tags (`<email>…</email>`), so the model knows what is content.
- **Role/system prompt** for stable behavior; **let it reason first** (a scratchpad field or thinking) for harder tasks; say what to do when information is missing (e.g. use `null`, don't guess).
- Iterate against real inputs and keep the failures.

# Structured output

Options (most reliable first): **tool/function calling with a JSON Schema** (force one tool with `tool_choice`), provider **structured-output** features, or plain prompting + validation. Always **validate** in your own code:

```python
from typing import Literal
from pydantic import BaseModel, Field, ValidationError

class Ticket(BaseModel):
    category: Literal["bug", "billing", "other"]
    priority: int = Field(ge=1, le=5)
    summary: str = Field(max_length=200)

import anthropic
client = anthropic.Anthropic()                         # reads ANTHROPIC_API_KEY from the environment
r = client.messages.create(
    model="claude-sonnet-5-5", max_tokens=512,
    tools=[{"name": "record", "description": "Record the ticket", "input_schema": Ticket.model_json_schema()}],
    tool_choice={"type": "tool", "name": "record"},
    messages=[{"role": "user", "content": f"<ticket>\n{text}\n</ticket>\nExtract the fields."}],
)
block = next(b for b in r.content if b.type == "tool_use")
ticket = Ticket.model_validate(block.input)            # raises ValidationError on bad data
print(r.usage.input_tokens, r.usage.output_tokens, r.stop_reason)
```

# Why validate even with a schema

Schema-following is not guaranteed in every mode; output can be **truncated** (`stop_reason == "max_tokens"`), refused, or have wrong types/enum values/extra prose; and **valid ≠ correct**: a well-formed answer can still be wrong or hallucinated. Validation catches structure; evals (week 14 day 3) catch correctness.

# Retry with the error

On `ValidationError`, send the model its previous output plus the error text and ask for a corrected version (max 1-2 retries). **Fixes:** formatting/type/constraint mistakes. **Doesn't fix:** information that isn't in the input (it will invent it), misunderstanding caused by a bad prompt, semantically wrong but valid answers. Count retries per case: a high rate means improve the prompt, not the retry loop.

# Instructions vs data (injection)

Anything inside the "data" part (emails, web pages) may contain text that _looks like instructions_. Models can't reliably tell the difference, so treat all such content as **untrusted**: delimit it, limit what the output can trigger, never let it choose privileges.

# Cost

`cost ≈ input_tokens × price_in + output_tokens × price_out`; log usage per call.

# 0/1 knapsack family

Pick each item **at most once**; 1D array, iterate capacity **downward**.

| Problem                                  | State                                 | Update                                                                 |
| ---------------------------------------- | ------------------------------------- | ---------------------------------------------------------------------- |
| **0/1 knapsack** (max value, capacity W) | `dp[w]` = best value                  | `dp[w] = max(dp[w], dp[w-wt] + val)`                                   |
| **Count subsets with sum K**             | `dp[s]` = ways                        | `dp[s] += dp[s-v]` (start `dp[0]=1`)                                   |
| **Min subset-sum difference**            | reachable sums up to `total/2`        | answer `total − 2·best` where `best` = largest reachable `s ≤ total/2` |
| **Count partitions with difference D**   | subsets with sum `S1 = (total + D)/2` | need `(total+D)` even and `≥ 0`                                        |

```python
def knapsack(wt: list[int], val: list[int], W: int) -> int:
    dp = [0] * (W + 1)
    for w_i, v_i in zip(wt, val):
        for w in range(W, w_i - 1, -1):
            dp[w] = max(dp[w], dp[w - w_i] + v_i)
    return dp[W]

def count_subsets(a: list[int], k: int) -> int:
    dp = [0] * (k + 1)
    dp[0] = 1
    for v in a:
        for s in range(k, v - 1, -1):
            dp[s] += dp[s - v]            # zeros double the count: correct
    return dp[k]
```

Why downward? Updating `dp[s]` from `dp[s-v]` that hasn't yet been updated this round guarantees item `v` is used once. Time O(n·W), space O(W).

# Keep keys out of code

- Read secrets from the **environment** (`os.environ["ANTHROPIC_API_KEY"]`, which raises `KeyError` if it is missing); the SDKs read it automatically. Fail fast if missing.
- Local dev: a `.env` file listed in `.gitignore`; commit `.env.example` with placeholders.
- **Never** commit keys, paste them in prompts/logs/screenshots, or ship them to a browser/mobile app (call the model from your **server**).
- Give each environment/service its own key; set **spend limits**; **rotate** regularly.
- If a key leaks: **revoke it immediately** (deleting the commit isn't enough), then rotate. Enable secret scanning (GitHub push protection, gitleaks) and pre-commit hooks.

1. **Validate anyway.** Output can be truncated, malformed, off-schema in some modes, or refused; and even valid JSON may be wrong. Code that consumes it must not trust it.
2. **Retry with error.** It fixes structural mistakes (missing field, wrong type/enum) because the model sees exactly what failed. It doesn't fix missing information in the input (it may invent a value), a poor prompt, or answers that are valid but wrong.
3. **Instructions vs data.** Instructions are your system/task text; data is the email/page content. If the data contains instructions, the model may follow them (prompt injection), so delimit it, treat it as untrusted, and limit what outputs can do.
