# Consensus

Get a cluster of nodes to **agree on a sequence of values** (a replicated log) despite crashes and message loss, as long as a **majority** is alive. **Raft** is designed for understandability: leader election + log replication + safety. A cluster of `2f+1` tolerates `f` failures.

# State and roles

```
Persistent (on disk before replying): currentTerm, votedFor, log[]
Volatile:                             commitIndex, lastApplied
Leader only:                          nextIndex[], matchIndex[]
Roles: Follower ⇄ Candidate → Leader
```

**Term** = logical clock; time is divided into terms, each with **at most one leader**. Any message carrying a **higher term** makes the receiver update its term and **step down to follower**.

# Leader election

1. A follower that hears nothing for a **randomized election timeout** (e.g. 150-300 ms) becomes a **candidate**: `currentTerm++`, votes for itself, sends `RequestVote(term, candidateId, lastLogIndex, lastLogTerm)` to all.
2. A node **grants** its vote if: `term ≥ currentTerm`, it hasn't voted for someone else this term (`votedFor` is null or this candidate), and the candidate's log is **at least as up-to-date** (higher last term, or equal term and longer log).
3. A candidate with **votes from a majority** becomes leader and immediately sends **heartbeats** (empty `AppendEntries`) to assert authority and reset followers' timers.
4. Split vote (no majority) → timeouts expire again; **randomization** makes one candidate time out first.

```
F ──timeout──► C ──majority──► L ──heartbeats──► F's (timers reset)
      ▲           │ higher term / valid leader seen
      └───────────┴──────► F
```

# Paxos, briefly

Paxos is the older consensus protocol Raft was designed to explain. A value is chosen in two phases, with three roles (**proposers**, **acceptors**, **learners**):

1. **Prepare:** a proposer picks a unique, increasing number `n` and asks a majority of acceptors to promise to ignore proposals numbered below `n`. Each acceptor replies with the highest-numbered proposal it has already accepted, if any.
2. **Accept:** the proposer sends `accept(n, v)`, where `v` must be the value of the highest-numbered accepted proposal it heard about (or its own value if none). Acceptors accept unless they promised a higher number. When a majority accept, the value is **chosen**.

The rule "adopt the highest value you hear about" is what keeps a chosen value from ever changing. Single-decree Paxos agrees on one value; Multi-Paxos repeats it for each log slot, with a stable leader skipping phase one. Raft gets the same guarantees with a clearer split into leader election, log replication and safety.

# Why safe

- **Randomized timeouts** prevent every node becoming a candidate at once and repeatedly splitting the vote.
- **One leader per term:** each node votes **at most once per term** (`votedFor` persisted before replying) and a leader needs a **majority**; any two majorities overlap in at least one node, so two candidates can't both win the same term.
- The log up-to-date rule ensures a new leader has all committed entries (next day).

# Node skeleton

```python
import enum, time
from dataclasses import dataclass, field

class Role(enum.Enum):
    FOLLOWER = 1
    CANDIDATE = 2
    LEADER = 3

@dataclass
class Entry:
    term: int
    cmd: object

@dataclass
class Raft:
    id: int
    n: int
    role: Role = Role.FOLLOWER
    current_term: int = 0
    voted_for: int = -1                              # -1 = none
    log: list[Entry] = field(default_factory=list)
    last_heard: float = field(default_factory=time.monotonic)
```

Run each node as an asyncio task on the `faultnet` event loop. There are no locks, but there is a new rule: **state can change at every `await`**, because other tasks run while you wait.

- **Ticker loop:** every ~10 ms (`await asyncio.sleep(0.01)`), if not leader and `now - last_heard > timeout` (random 150-300 ms, re-rolled each time) → `start_election()`.
- `start_election`: `current_term += 1`, `voted_for = id`, count votes = 1, send `RequestVote` to every peer as a separate task, and **re-check `role == CANDIDATE and term unchanged` after every `await`** when replies arrive. Become leader on majority.
- `RequestVote` handler: apply the three vote rules; persist `current_term`/`voted_for` (write and `os.fsync` before replying); reset the election timer **only when you grant** a vote.
- Leader: heartbeat every ~50 ms.
- Any RPC/reply with `term > current_term` → `current_term = term; role = FOLLOWER; voted_for = -1`.

# Tests (use faultnet + seed)

- Exactly **one leader** after startup (check `leaders per term ≤ 1` continuously). Run every test over many seeds with `@pytest.mark.parametrize("seed", range(50))`.
- Partition the leader away → the majority side elects a new leader with a higher term; heal → old leader steps down.
- No leader without a majority.

# Tree views (use level order or DFS with depth/column)

**Right side view:** last node of each level (BFS), or DFS visiting right first and recording the first node seen at each depth. **Left view:** first node of each level.

```python
def right_view(root: TreeNode | None) -> list[int]:
    res: list[int] = []

    def dfs(n: TreeNode | None, d: int) -> None:
        if n is None:
            return
        if d == len(res):
            res.append(n.val)              # first node reached at this depth (right first)
        dfs(n.right, d + 1)
        dfs(n.left, d + 1)

    dfs(root, 0)
    return res
```

**Top view / bottom view:** BFS with a **horizontal distance** `hd` (left child `hd-1`, right `hd+1`). **Top:** keep the **first** node seen per `hd`. **Bottom:** keep the **last** (overwrite). Output ordered by `hd`.

```python
from collections import deque

q = deque([(root, 0)])
top: dict[int, int] = {}
while q:
    n, hd = q.popleft()
    top.setdefault(hd, n.val)              # bottom view: always assign: top[hd] = n.val
    if n.left:
        q.append((n.left, hd - 1))
    if n.right:
        q.append((n.right, hd + 1))
view = [top[k] for k in sorted(top)]
```

**All root-to-leaf paths:** DFS with a path slice; at a leaf copy the path; backtrack by trimming.

```python
def dfs(n: TreeNode | None) -> None:
    if n is None:
        return
    path.append(n.val)
    if n.left is None and n.right is None:
        res.append(path.copy())            # copy at a leaf
    dfs(n.left)
    dfs(n.right)
    path.pop()                             # backtrack
```

Use BFS (not DFS) when "first by horizontal position, shallowest wins" matters.

# Debug distributed code

Non-determinism makes bugs hard to catch and to reproduce.

- **Log state transitions** with `node`, `term`, `role`, event, and a monotonically increasing sequence; one line per decision (`"S2 T5: vote granted to S1"`). Make logs greppable and sortable across nodes.
- Make runs **deterministic**: seeded RNG, injectable clock, a single-threaded event loop in tests when possible.
- **Run tests many times** (many seeds, `pytest --count`), because bugs show up 1 in 100.
- **Re-validate state (term, role) after every `await`** (and, in threaded code, never hold a lock across a network call).
- Visualize traces (ShiViz) and assert **invariants** continuously (e.g. at most one leader per term).
- Reduce the cluster to 3 nodes and shorten timeouts to reproduce quickly.

1. **Randomized timeouts.** If all followers used the same timeout they'd become candidates simultaneously, split the votes and repeat forever. Random timeouts make one node time out first, win the election and suppress the others with heartbeats.
2. **One leader per term.** Each server votes for at most one candidate per term (`votedFor` persisted), and winning needs a majority of votes. Two majorities share a server, so two different candidates can't both get a majority in the same term.
3. **Raft versus basic Paxos.** Basic Paxos agrees on a single value with symmetrical proposers, so a replicated log needs Multi-Paxos plus extra design (leader selection, log gaps, reconfiguration) that the paper leaves open. Raft makes a **strong leader** the core: elections choose one leader per term, only the leader appends entries and sends them to followers in order, and entries flow in one direction, so logs have no holes and the safety argument (log matching, election restriction) is simpler to state, teach and implement. Both tolerate `f` failures with `2f + 1` nodes and use majority quorums.
