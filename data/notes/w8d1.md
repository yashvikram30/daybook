# ACID

|                 | Meaning                                                     | Mechanism         |
| --------------- | ----------------------------------------------------------- | ----------------- |
| **A**tomicity   | all of a transaction or none of it                          | undo / log        |
| **C**onsistency | invariants (constraints) hold after commit                  | app + constraints |
| **I**solation   | concurrent transactions don't see each other's partial work | locks / MVCC      |
| **D**urability  | committed = survives a crash                                | WAL + fsync       |

# Write-ahead logging

**Rule:** the log record describing a change must be **durable (fsynced) before the changed data page** is written to disk; a transaction is **committed** only when its commit record is durable.

```
1. append  [LSN, txid, op, key, old, new]  to the log
2. append  [COMMIT txid]; fsync the log     ← now durable; reply "ok"
3. later: write dirty data pages (any time)
crash → recovery re-reads the log
```

- The log is **sequential** (cheap); data pages are random writes that can be **deferred**. That is why WAL is fast _and_ safe.
- **Steal / no-force:** the buffer pool may write dirty pages of _uncommitted_ transactions (steal) and need not flush pages at commit (no-force). This needs **undo** (to roll back stolen pages) and **redo** (to replay unflushed committed changes), which the log provides.

# Recovery (ARIES in three passes)

1. **Analysis:** from the last checkpoint, find active transactions and dirty pages.
2. **Redo:** _repeat history_: reapply every logged change not yet on the page (compare the page's LSN with the record's LSN).
3. **Undo:** roll back transactions with no commit record ("losers"), logging compensation records.

A **committed transaction whose pages never hit disk** is simply **redone** from the log.

**Checkpoints** bound how much log must be replayed.

# Group commit

`fsync` is the expensive step (ms). Collect log records from many concurrent transactions and **fsync once** for the batch: throughput rises sharply at the cost of a small latency wait.

```python
import os, queue, threading
from concurrent.futures import Future

class GroupCommitWAL:
    def __init__(self, f) -> None:
        self.f = f
        self.q: "queue.Queue[tuple[bytes, Future]]" = queue.Queue()
        threading.Thread(target=self._run, daemon=True).start()

    def append(self, rec: bytes) -> None:
        fut: Future = Future()
        self.q.put((rec, fut))
        fut.result()                      # blocks until the batch holding rec has been fsynced

    def _run(self) -> None:
        while True:
            batch = [self.q.get()]        # wait for the first record
            while True:                   # then take whatever else is already queued
                try:
                    batch.append(self.q.get_nowait())
                except queue.Empty:
                    break
            for rec, _ in batch:
                self.f.write(rec)
            self.f.flush()
            os.fsync(self.f.fileno())     # ONE fsync for the whole batch
            for _, fut in batch:
                fut.set_result(None)
```

# WAL for the KV store

1. Record: `len | crc | op(put/del) | klen | vlen | key | value`.
2. `Put(k,v)`: append the record to `wal.log`, `flush()` and `os.fsync`, **then** update the in-memory `dict`.
3. `Open`: replay `wal.log` from the start; stop at the first bad length/CRC (torn tail) and truncate. Replay must be **idempotent**.
4. **Checkpoint:** write a snapshot of the dict to a temp file, `os.fsync`, `os.replace`, then truncate the WAL.
5. **Group commit:** `put` enqueues its record on a `queue.Queue`; a single writer thread drains whatever is queued, writes it all, calls `os.fsync` **once**, then wakes each waiter (see the class above).

Measure: N concurrent writer threads, ops/s with per-write fsync vs group commit.

# Monotonic stack applications

**Next greater element II (circular):** loop `i` over `2n` indices (use `i % n`), push only in the first pass.

```python
res = [-1] * n
st: list[int] = []
for i in range(2 * n):
    while st and a[st[-1]] < a[i % n]:
        res[st.pop()] = a[i % n]
    if i < n:
        st.append(i)
```

**Asteroid collision:** stack of survivors; a new asteroid moving left (`<0`) collides while the stack top moves right (`>0`): compare sizes (equal → both die).

```python
st: list[int] = []
for x in ast:
    alive = True
    while alive and x < 0 and st and st[-1] > 0:
        top = st[-1]
        if top < -x:
            st.pop()
        else:
            alive = False
            if top == -x:
                st.pop()
    if alive:
        st.append(x)
```

**Sum of subarray minimums:** for each `i`, `left` = distance to the previous **strictly smaller**, `right` = distance to the next **smaller-or-equal** (tie-break so duplicates aren't double-counted); contribution `a[i]·left·right`; total mod 1e9+7 (Python ints do not overflow, so reduce at the end or as you go; in C or Java reduce as you go).

**Sum of subarray ranges** = Σ(max) − Σ(min), each via the same technique. O(n).

# Define invariants

An **invariant** is a statement that must be true at all times (or at defined points). Writing them down turns "it seems to work" into something testable.

Examples for a KV store:

- Every **acknowledged** write is readable after any crash and restart.
- A key is never visible with a value that was not written (no torn values).
- The in-memory index and the on-disk data agree.
- The log is a prefix-valid sequence: replay never errors on a clean shutdown.

Use them in **assertions**, **tests**, **property-based tests**, crash tests, and (for protocols) specs like **TLA+**. State invariants in comments next to the code that must preserve them.

1. **Log first.** If a data page reached disk and then the system crashed before the log record did, recovery would have no way to **undo** an uncommitted change (or know what changed). Log-before-data guarantees every on-disk change is described durably.
2. **Committed but unflushed.** Recovery **redoes** it: replays the logged changes onto pages whose LSN is older than the log record, so the committed effects are restored.
3. **The three recovery passes.** **Analysis** scans the log from the last checkpoint to rebuild which transactions were active at the crash and which pages may have been dirty. **Redo** repeats history: it reapplies every logged change (committed or not) whose effect is missing from the page, judged by comparing the page's LSN with the record's LSN, bringing the database to its state at the moment of the crash. **Undo** then rolls back the transactions that never committed (the "losers"), walking their records backwards and writing compensation log records so recovery itself is safe to repeat after another crash.
