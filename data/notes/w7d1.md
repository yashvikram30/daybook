# The relational model and SQL

A **relation** is a table: **rows** (tuples) of **columns** (attributes) with a fixed type each. A **primary key** uniquely identifies a row; a **foreign key** is a column whose values must exist as a key in another table, which is how tables refer to one another. A **database management system** (DBMS) stores the tables, answers declarative queries (you say _what_ you want, not how), and adds transactions, indexes and access control.

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE customers (id INTEGER PRIMARY KEY, name TEXT NOT NULL, city TEXT);
CREATE TABLE orders (id INTEGER PRIMARY KEY, customer_id INTEGER REFERENCES customers(id), total REAL);
INSERT INTO customers VALUES (1, 'Ada', 'London'), (2, 'Lin', 'Oslo');
INSERT INTO orders VALUES (1, 1, 30.0), (2, 1, 12.5), (3, 2, 99.0);
""")
rows = db.execute("""
SELECT c.name, COUNT(*) AS n, SUM(o.total) AS spent
FROM customers c JOIN orders o ON o.customer_id = c.id
WHERE o.total > 10
GROUP BY c.name
HAVING SUM(o.total) > 40
ORDER BY spent DESC
""").fetchall()
print(rows)    # [('Lin', 1, 99.0), ('Ada', 2, 42.5)]
```

Read a query in this order: `FROM`/`JOIN` (which rows), `WHERE` (filter rows), `GROUP BY` (form groups), `HAVING` (filter groups), `SELECT` (compute columns), `ORDER BY`, `LIMIT`. Use placeholders (`?`) for values, never string formatting.

# Normal forms: why tables are split

Storing the same fact in many places lets copies disagree (**update anomaly**), makes some facts impossible to store without others (**insertion anomaly**), and loses facts on delete (**deletion anomaly**). **Normalisation** removes this using **functional dependencies**: `X → Y` means the value of `X` determines the value of `Y` (an order id determines its customer).

| Form | Rule                                                             | Typical fix                                                                               |
| ---- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 1NF  | every cell holds one atomic value; no repeating groups           | split a "phone1, phone2" column into rows                                                 |
| 2NF  | 1NF, and no non-key column depends on _part_ of a composite key  | move the partly dependent column to its own table                                         |
| 3NF  | 2NF, and no non-key column depends on another non-key column     | `orders(customer_id, customer_city)`: city depends on customer, so move it to `customers` |
| BCNF | every determinant (left side of a dependency) is a candidate key | decompose until each dependency is keyed                                                  |

A good design has each fact in exactly one place, found through a key. **Denormalisation** (deliberately copying a value) is a performance choice you make later and pay for with extra care on writes.

# Why pages

Storage moves data in blocks, so databases do I/O in fixed-size **pages** (SQLite 4 KB default, Postgres 8 KB, InnoDB 16 KB). A page is the unit of I/O, caching, locking and recovery. Fixed size makes addressing trivial: page _n_ is at offset `n × pageSize`.

# Slotted page

```
| header: nSlots, freeStart, freeEnd |
| slot0 | slot1 | slot2 | ...  →  grows right        (each slot = offset, length)
|               ... free space ...                    |
|        ← tuples grow left | tuple2 | tuple1 | tuple0 |
```

- A tuple is addressed by **(pageID, slotID)** (a record id). Tuples can move within the page (compaction) while the **slot** keeps its id, so external references stay valid.
- **Delete:** mark the slot empty (offset 0/length 0), reuse later; compact when fragmented.
- **Insert:** needs `len + slotSize ≤ free space`; else use another page.
- Variable-length fields use offsets; huge values go to **overflow pages** (Postgres TOAST).
- Rows can live in a **heap file** (unordered, plus separate indexes) or inside a clustered B-tree (SQLite, InnoDB).

```python
PAGE_SIZE = 4096
page = bytearray(PAGE_SIZE)                      # header fields via struct.unpack_from("<H", page, 0) ...
```

# Buffer pool

A cache of pages in RAM: `pageID → frame`, with per-frame **pin count** and **dirty bit**. It decides **which pages stay in memory**, when to **write back** dirty ones, and **what to evict**. Policies: **LRU**, **Clock** (cheap LRU approximation), **LRU-K**; scans can flood a plain LRU, so databases use scan-resistant variants. Pinned pages can't be evicted; a dirty page may only be written after its log records (**write-ahead rule**). Databases manage their own pool rather than the OS cache for control over eviction and flush order.

# Inspecting SQLite

`sqlite3 test.db '.dbinfo'` (page size, count), or from Python `sqlite3.connect("test.db").execute("PRAGMA page_size")` and `PRAGMA page_count`; `xxd -l 100 test.db`: the 100-byte header starts with `SQLite format 3\0`; page size is at offset 16 (big-endian).

# Slotted page in Python

```python
import struct

PAGE_SIZE = 4096

class Page:
    # header: [0:2] n_slots  [2:4] free_end (start of tuple area, begins at 4096)
    # slot i: [4+4i : 6+4i] offset, [6+4i : 8+4i] length
    def __init__(self, buf: bytearray | None = None) -> None:
        if buf is None:
            buf = bytearray(PAGE_SIZE)
            struct.pack_into("<HH", buf, 0, 0, PAGE_SIZE)
        self.b = buf

    def insert(self, t: bytes) -> int | None:
        n, end = struct.unpack_from("<HH", self.b, 0)
        slots_end = 4 + 4 * (n + 1)                   # header + slot array incl. new slot
        if end - len(t) < slots_end:
            return None                               # no room
        end -= len(t)
        self.b[end:end + len(t)] = t
        struct.pack_into("<HH", self.b, 4 + 4 * n, end, len(t))
        struct.pack_into("<HH", self.b, 0, n + 1, end)
        return n
```

`get(slot)`: read `(off, length)` with `unpack_from`, return `bytes(self.b[off:off + length])` (check for deleted). `delete`: set `length = 0`. Optionally `compact()`.

# Counting subarrays with a window

Windows can count _"at most K"_ easily; **exactly K = at_most(K) − at_most(K−1)**.

```python
from collections import Counter

def at_most(a: list[int], k: int) -> int:           # subarrays with at most k distinct values
    cnt: Counter[int] = Counter()
    l = res = 0
    for r, v in enumerate(a):
        cnt[v] += 1
        while len(cnt) > k:
            cnt[a[l]] -= 1
            if cnt[a[l]] == 0:
                del cnt[a[l]]
            l += 1
        res += r - l + 1                            # all windows ending at r that start in [l, r]
    return res
# subarrays with exactly k distinct = at_most(k) - at_most(k - 1)
```

| Problem                                      | Reduction                                                     |
| -------------------------------------------- | ------------------------------------------------------------- |
| Subarrays with K different integers          | `at_most(K) − at_most(K−1)`                                   |
| Binary subarrays with sum S                  | `at_most(S) − at_most(S−1)` (or prefix sums + map)            |
| Count nice subarrays (exactly K odd numbers) | map to 0/1 (`v%2`), same as above                             |
| Substrings containing a, b **and** c         | for each `r`, let `m = min(lastA, lastB, lastC)`; add `m + 1` |

`at_most(0)` for the sum version is the count of all-zero runs.

# SQL fluency

Logical evaluation order: `FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`. (So `WHERE` can't use aggregates or select aliases; `HAVING` can use aggregates.)

```sql
SELECT c.name, COUNT(o.id) AS orders, SUM(o.total) AS spent
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
WHERE c.country = 'IN'
GROUP BY c.id, c.name
HAVING SUM(o.total) > 100
ORDER BY spent DESC LIMIT 10;
```

| Join  | Keeps                             |
| ----- | --------------------------------- |
| INNER | matching rows only                |
| LEFT  | all left rows, NULLs for no match |
| FULL  | all rows from both                |
| CROSS | every combination                 |

- **NULL** is "unknown": `x = NULL` is never true; use `IS NULL`; `NULL` in `NOT IN (...)` poisons the result.
- Window functions: `ROW_NUMBER() OVER (PARTITION BY k ORDER BY t)`.
- CTEs: `WITH x AS (...) SELECT ...`.

1. **Fixed pages.** I/O devices move blocks, so reading a few bytes costs a whole block anyway. Fixed size enables simple addressing (`offset = id × size`), whole-page caching, atomic-ish page writes, free-space reuse without fragmentation at the file level, and a uniform unit for locks and logging.
2. **Buffer pool.** It decides which pages are cached, when dirty pages are flushed and which to evict when full (respecting pins and the WAL rule). Use a scan-resistant policy such as LRU-K (Clock is only a cheap approximation of LRU and does not stop a big scan from evicting hot pages by itself).
3. **Primary key versus index.** A **primary key** guarantees that every row has a value, that the value is **unique**, and so identifies exactly one row (it is a constraint on the data, and the foreign keys of other tables point at it). It says nothing about _how fast_ a row can be found. An **index** is an extra sorted (or hashed) structure that makes lookups by that column fast, so a table scan is not needed. Databases usually create an index on the primary key to enforce uniqueness cheaply, but an index on any other column (not unique, or composite) speeds queries without adding any guarantee about the data.
