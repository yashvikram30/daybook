# What TLS gives you

**Confidentiality** (encryption), **integrity** (tamper detection), **authentication** (you're talking to the real server, optionally the client too). It runs between TCP and HTTP.

- **Asymmetric** crypto (key exchange, signatures): slow, used to agree on keys and prove identity.
- **Symmetric** AEAD ciphers (AES-GCM, ChaCha20-Poly1305): fast, used for all application data.

# TLS 1.3 handshake (1 round trip)

```
Client                                         Server
 ClientHello: versions, ciphers, key_share(ECDHE pub) ─────►
                                    ◄───── ServerHello: cipher, key_share(ECDHE pub)
   [both compute the shared secret → handshake keys; everything below is encrypted]
                                    ◄───── EncryptedExtensions, Certificate,
                                           CertificateVerify (signature), Finished
 Finished ─────────────────────────────────────────────────►
 ◄══════════ application data, encrypted with session keys ═══════════►
```

- **Certificate:** server's public key bound to its domain name by a CA's signature.
- **CertificateVerify:** server signs the handshake transcript with its private key, proving it owns the key.
- **Finished:** MAC over the whole handshake; detects tampering/downgrade.
- TLS 1.2 needed 2 RTT; 1.3 removed weak ciphers and RSA key transport.

# The cryptography underneath

**Symmetric** ciphers (AES, ChaCha20) use one shared key to encrypt and decrypt. They are fast, but the two sides must first agree on the key without an eavesdropper learning it.

**Asymmetric** (public-key) cryptography gives each party a _public key_ anyone may see and a _private key_ that is never shared. Data encrypted with the public key can only be decrypted with the private key; a message _signed_ with the private key can be verified with the public key. It is hundreds of times slower, so TLS uses it only to agree on a symmetric key and to prove identity.

**RSA** in miniature (real keys use primes of 1000+ bits):

1. Pick primes `p = 61`, `q = 53`. Then `n = p·q = 3233` and `φ = (p−1)(q−1) = 3120`.
2. Pick a public exponent `e = 17` (coprime to φ). The private exponent `d` satisfies `e·d ≡ 1 (mod φ)`: `d = 2753`.
3. Public key `(n, e)`; private key `(n, d)`. Encrypt `m = 65`: `c = m^e mod n = 2790`. Decrypt: `c^d mod n = 65`.

```python
n, e, d = 3233, 17, 2753
c = pow(65, e, n)          # 2790
print(c, pow(c, d, n))     # 2790 65
```

Its safety rests on factoring `n` back into `p` and `q` being infeasible for large `n`. **Diffie-Hellman** solves the key-agreement problem differently: both sides pick secrets, exchange `g^secret mod p`, and each raises what they received to their own secret to reach the same number. With `p = 23`, `g = 5`, secrets 6 and 15, they exchange 8 and 19 and both compute 2. TLS 1.3 uses the elliptic-curve version (ECDHE) with fresh keys every session, which is what gives forward secrecy.

# What a certificate proves

It says: _the holder of this private key was validated by a CA as controlling this domain name._ Verification checks: (1) signature chain **leaf → intermediate → root**, ending at a root in the client's **trust store**; (2) **validity dates**; (3) **hostname matches** a Subject Alternative Name; (4) key usage/constraints; (5) revocation status (OCSP stapling, CRLs). It does **not** prove the site is honest. CAs vouch; Certificate Transparency logs make mis-issuance detectable.

# Forward secrecy

Each session uses **ephemeral** (EC)DHE keys that are discarded afterwards, so stealing the server's long-term private key later cannot decrypt recorded old traffic. Provided by the **ephemeral key exchange** (`key_share`) in the handshake; mandatory in TLS 1.3.

# In Python

```python
import socket, ssl

ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
ctx.minimum_version = ssl.TLSVersion.TLSv1_2
ctx.load_cert_chain("cert.pem", "key.pem")

with socket.create_server(("", 8443)) as srv:
    conn, _ = srv.accept()
    with ctx.wrap_socket(conn, server_side=True) as tls:      # the handshake happens here
        print(tls.version(), tls.cipher())                    # e.g. 'TLSv1.3' and the cipher suite
```

For a client use `ssl.create_default_context()`: it verifies the certificate chain **and** the hostname against the system trust store. Never turn that off in production (`check_hostname = False`, `verify_mode = ssl.CERT_NONE`, or `verify=False` in `requests`). With asyncio pass the context to `asyncio.start_server(handler, host, port, ssl=ctx)`.

# Steps

1. `mkcert -install` (adds a local CA to your trust store), then `mkcert localhost 127.0.0.1 ::1` → `localhost+2.pem`, `localhost+2-key.pem`.
2. Wrap your server's accepted connections with an `ssl.SSLContext` that loads `localhost+2.pem` and `localhost+2-key.pem` on port 8443. `curl -v https://localhost:8443/` should verify without `-k`.
3. `openssl s_client -connect localhost:8443 -tls1_3 -servername localhost` : read **Protocol/Cipher** (e.g. `TLS_AES_256_GCM_SHA384`), the **certificate chain**, and `Verify return code`.
4. Capture on `lo0` in Wireshark: ClientHello (visible SNI, key_share), ServerHello, then encrypted records. Match each message to tls13.xargs.org.
5. Write the note: chain (leaf → mkcert CA), and the five checks above.

# Pitfalls

- Never commit `*-key.pem`; add to `.gitignore`.
- mkcert CA is for local dev only; never share its root key.

# Sliding window

For **contiguous** subarray/substring problems. Two pointers `l`, `r`; expand `r`, shrink `l` while the window is invalid. Each index enters and leaves once: **O(n)**.

```python
l = best = 0
for r in range(len(s)):
    add(s[r])
    while not valid():
        remove(s[l])
        l += 1
    best = max(best, r - l + 1)
```

| Problem                                  | Window state                                 | Valid when                      |
| ---------------------------------------- | -------------------------------------------- | ------------------------------- |
| Longest substring w/o repeats            | last index per char / set                    | no duplicates                   |
| Max consecutive ones III                 | zero count                                   | zeros ≤ k                       |
| Fruit into baskets                       | counts map                                   | ≤ 2 distinct types              |
| Max points from cards (take k from ends) | fixed window of size `n-k` of the **middle** | answer = total − min window sum |

```python
# longest substring without repeating characters
last: dict[str, int] = {}
l = best = 0
for r, ch in enumerate(s):
    if ch in last and last[ch] >= l:
        l = last[ch] + 1
    last[ch] = r
    best = max(best, r - l + 1)
```

**Fixed window:** slide by adding the new element and removing the one leaving.

# Secrets and configuration

**Config** that varies per environment (URLs, ports, credentials) lives in the **environment**, not in code (Twelve-Factor).

```python
import os, sys

key = os.environ.get("API_KEY")
if not key:
    sys.exit("API_KEY is required")        # fail fast
```

- Never commit secrets (keys, tokens, private certs, `.env`); add them to `.gitignore`, commit `.env.example` with fake values.
- Don't log secrets; redact in errors.
- Use a secret manager (or CI secrets) in production; give each service its own least-privilege credentials; **rotate** them.
- If a secret is committed, treat it as **leaked**: revoke/rotate it (deleting the commit isn't enough). Use secret scanning (e.g. gitleaks, GitHub push protection).
