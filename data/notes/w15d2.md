# RAG in one picture

```
ingest:   documents → parse/clean → CHUNK → embed + keyword index (+ metadata) → store
query:    question → retrieve (vector + keyword) → FUSE → RERANK → top few chunks → prompt → LLM answer
```

Most RAG failures are **retrieval failures**: if the right chunk isn't in the prompt, the model can't use it.

# Chunking

| Too small                                                                           | Too large                                                                                                 |
| ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| fragments lack context; the answer is split across chunks; many near-duplicate hits | embedding blurs several topics; noisy text wastes context and money; answer buried ("lost in the middle") |

Typical start: **200-800 tokens**, 10-20% **overlap**. Strategies: **fixed-size** (+overlap), **recursive** (paragraph → sentence), **structure-aware** (by heading/section, often best for docs), **sentence windows** (embed a sentence, return its neighbors). Store with every chunk: **source URL, title, heading path, content hash**, position.

# Keyword search: BM25

Lexical ranking: `score(q,d) = Σ_t IDF(t) · tf·(k1+1) / (tf + k1·(1 − b + b·|d|/avgdl))` (`k1≈1.2-2`, `b≈0.75`): rewards rare terms, saturates term frequency, normalizes length. **Strong on exact tokens** (error codes `ECONNRESET`, function names, IDs, rare jargon) which embeddings blur; **weak on synonyms/paraphrase**. Embeddings are the reverse; so combine them.

# Hybrid: Reciprocal Rank Fusion

Merge rankings without comparing incomparable scores: `RRF(d) = Σ_rankings 1/(k + rank(d))`, `k = 60`.

```python
def rrf(rankings, k=60):
    s = {}
    for r in rankings:
        for rank, doc in enumerate(r, 1): s[doc] = s.get(doc, 0) + 1 / (k + rank)
    return sorted(s, key=s.get, reverse=True)
```

# Reranking

- **Bi-encoder (embeddings):** query and document encoded **separately** (document vectors precomputed) → fast, approximate.
- **Cross-encoder:** feeds `[query, document]` **together** through the transformer, so every query token can attend to every document token → much more accurate, but one forward pass **per pair**, so only rerank the **top 20-100** candidates.

```python
from sentence_transformers import CrossEncoder
ce = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
scores = ce.predict([(query, c.text) for c in candidates])
```

# Lost in the middle

LLMs use information at the **start and end** of a long context better than the middle, so stuffing in more chunks can _hurt_. Prefer **fewer, better** chunks.

# Three chunkers

1. **Fixed:** 500 tokens (or ~2,000 chars), 50 overlap.
2. **By heading:** split on `#`/`<h2>`; keep `heading_path`; split long sections.
3. **Sentence windows:** one sentence indexed, ±2 sentences returned as context.
   Store all three under different `chunker` names so retrieval can be compared later.

# Retrieval stages

- Vectors (hnswlib/pgvector) top 50 → BM25 (`rank_bm25`, or Postgres FTS: `to_tsvector('english', text) @@ plainto_tsquery('english', $1)` ordered by `ts_rank_cd`; note this is not exactly BM25) top 50 → **RRF** → top 20 → **cross-encoder** → top 5.
- Inspect 10 queries, including **exact-term** ones (`"ERROR 23505"`), **paraphrases** and **vague** ones. For each stage note which helped or hurt; keep a notes table.

# Idempotency check

Run ingestion twice: row counts and ids must be identical; changing one doc changes only its chunks.

# Edit distance and string matching DP

**Edit distance** (insert, delete, replace, cost 1 each):

```python
dp = [[0] * (n + 1) for _ in range(m + 1)]
for i in range(m + 1):
    dp[i][0] = i
for j in range(n + 1):
    dp[0][j] = j
for i in range(1, m + 1):
    for j in range(1, n + 1):
        if s[i - 1] == t[j - 1]:
            dp[i][j] = dp[i - 1][j - 1]
        else:
            dp[i][j] = 1 + min(dp[i - 1][j], dp[i][j - 1], dp[i - 1][j - 1])   # delete, insert, replace
```

**Shortest common supersequence:** length `m + n − LCS`; build it by walking back through the LCS table (emit the shared char once, otherwise the char from the string you moved along).

**Distinct subsequences** (how many times `t` appears as a subsequence of `s`): `dp[i][j] = dp[i-1][j] + (s[i-1]==t[j-1] ? dp[i-1][j-1] : 0)`, `dp[i][0] = 1`.

**Wildcard matching** (`?` = any one char, `*` = any sequence incl. empty): `dp[i][j]` = pattern `p[:i]` matches `s[:j]`:

- `p[i-1]=='*'`: `dp[i-1][j] || dp[i][j-1]` (star matches empty, or one more char)
- `'?'` or equal char: `dp[i-1][j-1]`; `dp[0][0] = true`, leading `*`s match the empty string.

All O(mn) time (rolling row for space).

# Idempotent pipelines

An ingestion job will be retried, rerun after a crash, and run on overlapping data. **Running it twice must give the same state as running it once.**

- **Deterministic ids:** derive each chunk's id from its content/source (`sha256(url + chunker + text)`); **upsert** by id instead of insert.
- **Skip unchanged:** compare a document's content hash with the stored one; re-embed only changed chunks (embedding calls cost money).
- **Handle deletes:** remove chunks whose source disappeared or whose hash changed (mark/sweep with a run id).
- **Atomic publish:** write to a new index/version, then switch (so queries never see half-ingested data).
- **Checkpoint** progress; make each step safe to repeat; log counts (added/updated/skipped/deleted).
- Keep chunking and embedding **deterministic and versioned** (store the chunker and embedding model version with each chunk).

1. **Error codes with BM25.** Exact tokens like `ECONNRESET` or `parseConfig` are rare, high-IDF terms that BM25 matches literally. Embeddings compress text into a semantic vector and blur or mis-tokenize rare identifiers, so exact lookups can rank poorly.
2. **Cross-encoder.** It sees the query and document **together**, so attention operates across both and can judge fine relations (negation, constraints). A bi-encoder embeds each separately and compares only the final vectors.
3. **Chunk size.** Too small: fragments lose context, answers are split, redundant hits. Too large: diluted embeddings, noise, more tokens/cost, and relevant text buried in the middle of the context.
