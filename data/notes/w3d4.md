# Pipes

A pipe is a kernel buffer with a **read end** and a **write end** (two fds). Writes block when full, reads block when empty; read returns **EOF only when all write ends are closed**, so close unused ends.

`a | b | c`: the **shell** creates each pipe _before_ starting the processes; `a`'s stdout = write end, `b`'s stdin = read end, etc. All processes run **concurrently**; the shell waits for all.

```python
import subprocess

p1 = subprocess.Popen(["ls"], stdout=subprocess.PIPE)
p2 = subprocess.Popen(["wc", "-l"], stdin=p1.stdout)
p1.stdout.close()          # parent closes its copy of the read end, or p1 never gets SIGPIPE if p2 exits early
p2.wait()
p1.wait()
```

The raw version: `r, w = os.pipe()`, then in each forked child `os.dup2(w, 1)` or `os.dup2(r, 0)` and close every other copy of `r` and `w` before `exec`.

# Interprocess communication

Processes have separate address spaces, so they need an explicit channel. There are two families.

|        | Shared memory                                                      | Message passing                                                       |
| ------ | ------------------------------------------------------------------ | --------------------------------------------------------------------- |
| How    | processes map the same region and read and write it directly       | processes call `send` and `receive`; the kernel copies the data       |
| Speed  | fastest: no copy after setup, no kernel call per access            | slower: a system call and a copy per message                          |
| Safety | you must synchronise yourself (locks, semaphores) or you get races | the kernel orders and buffers messages, so it is simpler to get right |
| Python | `multiprocessing.shared_memory`, `mmap`                            | pipes, `socket.socketpair`, `multiprocessing.Queue`                   |

Message passing has design choices: **direct** (name the other process) or **indirect** (use a mailbox or port that several processes share), and **blocking** (wait until the message is sent or received) or **non-blocking**. A pipe is indirect and blocking with a bounded buffer. Sockets are the same idea across machines, which is where week 5 starts.

# Signals

Asynchronous notifications to a process.

| Signal                   | Default         | Notes                                            |
| ------------------------ | --------------- | ------------------------------------------------ |
| `SIGINT` (2)             | terminate       | Ctrl-C; sent to the **foreground process group** |
| `SIGTERM` (15)           | terminate       | polite stop; catchable                           |
| `SIGKILL` (9), `SIGSTOP` | kill / stop     | **cannot be caught, blocked or ignored**         |
| `SIGTSTP` / `SIGCONT`    | stop / continue | Ctrl-Z, `fg`/`bg`                                |
| `SIGCHLD`                | ignore          | a child changed state                            |
| `SIGPIPE`                | terminate       | write to a pipe with no readers                  |

```python
import signal

def on_int(signum, frame):
    print("caught", signal.Signals(signum).name)

signal.signal(signal.SIGINT, on_int)    # replaces the default (which raises KeyboardInterrupt)
signal.signal(signal.SIGTSTP, signal.SIG_IGN)
signal.pause()                          # sleep until a signal arrives
```

A Python handler does not run at the instant the signal arrives. A low-level handler just sets a flag, and the interpreter runs your function in the **main thread** between bytecodes. Handlers can only be installed from the main thread. By default Python turns `SIGINT` into a `KeyboardInterrupt` exception.

# Waiting for many things: selectors

A shell, a server or a chat client must watch several file descriptors and react to whichever is ready, without one blocking the rest. `selectors` wraps the OS call (`epoll` on Linux, `kqueue` on macOS):

```python
import selectors, socket

sel = selectors.DefaultSelector()
a, b = socket.socketpair()
sel.register(a, selectors.EVENT_READ)
b.send(b"hello")
for key, _events in sel.select(timeout=1):     # blocks until a registered fd is ready
    print(key.fileobj.recv(100))
```

The call returns only the descriptors that are ready, so you never block on a quiet one. This is the loop `asyncio` runs underneath. Handlers installed with `signal.signal` interrupt this wait, which is why the self-pipe trick (a signal handler writes one byte to a pipe the selector watches) is common.

# Process groups and job control

Each job is a **process group** (`start_new_session=True`, `process_group=0` or `os.setpgid`); the terminal has one _foreground_ group which receives Ctrl-C/Ctrl-Z. The shell must ignore SIGINT itself while a foreground job runs, put background jobs (`&`) in their own groups and not wait on them synchronously.

# Zombies and orphans

- **Zombie:** child exited but the parent hasn't `wait`ed; only its exit status entry remains. Fix: reap (e.g. call `proc.wait()` from a small thread, or `os.waitpid(-1, os.WNOHANG)` for background jobs).
- **Orphan:** parent died first; adopted by init/subreaper (pid 1), which reaps it.

# Ctrl-C handling

```python
signal.signal(signal.SIGINT, lambda *_: print())          # shell survives; print a newline
proc = subprocess.Popen(args, process_group=0)             # job in its own group (Python 3.11+)
```

The terminal sends SIGINT to the _foreground group_. When a job is in its own group, it also has to be made the terminal's foreground group (`os.tcsetpgrp(tty_fd, pgid)`, with `SIGTTOU` ignored in the shell while you do it) to receive Ctrl-C, and the shell takes the terminal back afterwards. Test with `sleep 100` then Ctrl-C.

# Binary search: the template

Search a **sorted** range in O(log n). Use a half-open interval `[lo, hi)` and one invariant.

```python
# lower bound: first index i with a[i] >= x  (len(a) if none)
def lower_bound(a: list[int], x: int) -> int:
    lo, hi = 0, len(a)
    while lo < hi:
        mid = lo + (hi - lo) // 2        # Python ints cannot overflow, but keep the habit for Java and C++
        if a[mid] >= x:
            hi = mid
        else:
            lo = mid + 1
    return lo
# upper bound: first i with a[i] > x  -> change the test to a[mid] > x
```

| Query                   | Answer                                       |
| ----------------------- | -------------------------------------------- |
| Exists?                 | `i = lower_bound(a, x); i < n and a[i] == x` |
| Insert position         | `lower_bound`                                |
| First / last occurrence | `lower_bound(x)` / `upper_bound(x)-1`        |
| Count of x              | `upper_bound - lower_bound`                  |
| Floor (largest ≤ x)     | `upper_bound(x) - 1` (if ≥ 0)                |
| Ceil (smallest ≥ x)     | `lower_bound(x)` (if < n)                    |

Python stdlib: `bisect.bisect_left` is `lower_bound` and `bisect.bisect_right` is `upper_bound`. Write your own first, then check it against them.

# Read other people's code

Most of the job is reading. Method:

1. Start from the **entry point** (`main`, a route, a test) and follow one request/path end to end.
2. Read **tests** first: they show intended behavior.

1. **Pipe setup.** The shell creates the pipe first (so both children inherit it), then starts the processes; they run concurrently, with `a` writing and `b` reading. The shell closes its own copies of both ends so EOF can be delivered, then waits for all.
2. **Parent never waits.** The exited child stays a **zombie** (exit status retained in the process table, resources mostly freed) until the parent waits or itself exits; then init adopts and reaps it. Many zombies can exhaust the pid table.
3. **Shared memory or message passing.** Choose **shared memory** when processes on one machine exchange large amounts of data often: after setup there is no copy and no system call per access, so it is the fastest. It gives up safety: you must synchronise access yourself or you get races. Choose **message passing** (pipes, sockets, queues) when the data is small or the processes are loosely coupled, or may be on different machines: the kernel buffers and orders messages, so it is simpler and safer, and it gives up speed (a system call and a copy per message) and needs a protocol for message boundaries.
