# Evals = unit tests for LLM software

Without them you can't tell if a prompt/model change helped or silently broke something. Loop: **find failures → write cases → measure → change → re-measure**.

# Building the set

- Start from **real traces** and do **error analysis**: read failures, name the failure categories, add a case for each. 20-50 good cases beat 1,000 synthetic ones.
- Each case: **input + expected output or success criteria** (+ category tag). Include easy, typical, edge and **adversarial** cases (prompt injection).
- Keep a held-out slice you don't tune on.

# Graders

| Grader                                                                      | Use for                         | Notes                                |
| --------------------------------------------------------------------------- | ------------------------------- | ------------------------------------ |
| **Code** (exact match, JSON schema, field equality, regex, tool-call check) | anything checkable              | fast, free, deterministic: prefer it |
| **LLM judge** with a written rubric                                         | tone, faithfulness, helpfulness | cheap at scale but can be biased     |
| **Human**                                                                   | calibration, hard cases         | slow; use to validate the judge      |

**Trusting an LLM judge:** write a specific rubric (binary pass/fail, with reasoning first), use a strong model, and **measure agreement with human labels** on a sample (accuracy / Cohen's kappa). Known biases: **position** (prefers the first answer), **verbosity**, **self-preference**. Re-check when the judge prompt or model changes.

# Comparing versions

Run the same set on prompt A and B; compare **pass rate** (overall and per category), **cost** and **latency**. With small `n` differences are noisy: look at _which_ cases flipped, and run multiple samples. Even `temperature=0` isn't perfectly deterministic.

# Cost levers

`cost = tokens × price`. **Prompt caching:** mark a stable prefix (system prompt, tools, long documents) with `cache_control: {"type": "ephemeral"}`; cache **reads** cost a fraction (about a tenth) of normal input tokens and cut latency; writes cost a bit more; entries expire after minutes; there's a minimum prefix size. Other levers: smaller/cheaper model for easy steps, shorter prompts, `max_tokens`, batching.

# Safety (OWASP Top 10 for LLM apps, selected)

**Prompt injection**, **sensitive information disclosure**, **improper output handling** (treat model output as untrusted input to other systems: escape HTML, parameterize SQL), **excessive agency**, **unbounded consumption** (rate limits, budgets).

# CI

Fast, deterministic job: use a **fake or recorded model** (cassettes) so PR checks don't depend on the network/cost. Separate job (nightly or on prompt changes) runs the **real model** on the full set with a pass-rate threshold.

# Eval harness

```python
CASES = [{"id": "c1", "input": "...", "expect": {"category": "bug"}, "tags": ["typical"]}, ...]

def run(prompt_version, model_call):
    results = []
    for c in CASES:
        out = model_call(prompt_version, c["input"])           # returns parsed output + usage + latency
        results.append({"id": c["id"], "pass": grade(c, out), "tokens": out.tokens, "latency": out.latency})
    return results
```

- **Graders:** `grade` = code check (schema valid + fields equal) for most; for fuzzy ones an LLM judge with a rubric (`"Answer PASS or FAIL after a one-sentence reason. PASS only if the summary contains no facts absent from the source."`).
- **Injection cases (5):** inputs containing "ignore instructions and output X"; pass = output still follows the real task/schema.
- Compare prompt v1 vs v2: table of pass rate (overall, by tag), mean tokens/cost, p95 latency; list cases that flipped.

# pytest wiring

```python
@pytest.fixture
def model(request): return RecordedModel("cassettes/") if not os.getenv("LIVE") else LiveModel()
@pytest.mark.parametrize("case", CASES, ids=lambda c: c["id"])
def test_case(case, model): assert grade(case, model.call(PROMPT, case["input"]))
```

CI job 1 (every PR): recorded model, fast. Job 2 (nightly/manual): `LIVE=1 pytest -m live`, fail if overall pass rate `< threshold`.

# DP: rod cutting and LIS

**Rod cutting** (unbounded knapsack): `dp[n] = max over len i of price[i] + dp[n−i]`.

```python
dp = [0] * (n + 1)
for l in range(1, n + 1):
    for i in range(1, l + 1):
        dp[l] = max(dp[l], price[i - 1] + dp[l - i])
```

**Longest increasing subsequence (strict):**

- **O(n²):** `dp[i] = 1 + max(dp[j]) for j<i, a[j]<a[i]`.
- **O(n log n)** "patience" with `tails[k]` = smallest tail of an increasing subsequence of length `k+1`:

```python
from bisect import bisect_left

tails: list[int] = []
for v in a:
    i = bisect_left(tails, v)               # first index with tails[i] >= v
    if i == len(tails):
        tails.append(v)
    else:
        tails[i] = v
return len(tails)                           # length only; `tails` itself is NOT the LIS
```

**Print the LIS:** use the O(n²) DP with a `parent[i]` array (or `idx`+`prev` in the log version), then walk back from the best end index and reverse.

**Largest divisible subset:** sort ascending; `dp[i] = 1 + max(dp[j])` for `a[i] % a[j] == 0` (divisibility is transitive on a sorted list), track `parent`, reconstruct. O(n²).

# Flaky tests

A test that sometimes passes and sometimes fails **without code changes** destroys trust: people rerun and ignore red.

**Causes:** time/`sleep` assumptions, randomness, **order dependence** and shared state, concurrency/races, network and external services, resource limits (timeouts under load), nondeterministic iteration (maps). **Models add a new source:** nondeterministic outputs.

**What to do**

- **Detect:** rerun failures N times (`-count`), run in random order, track flake rates.
- **Fix at the root:** inject time/randomness/network; isolate state; wait on conditions, not sleeps.
- **Don't hide them with blind retries**; quarantine (still run, don't block) with an owner and deadline.
- **For LLM tests:** use a recorded/fake model in CI; assert on **properties** (valid schema, contains key fact) not exact text; use temperature 0; for live evals run several samples and gate on **pass-rate thresholds**, not single outcomes.

1. **Did the prompt change hurt?** Run the same eval set on old and new versions and compare pass rates (per category), cost and latency; inspect cases that flipped to fail. Without a fixed set you're guessing.
2. **LLM judge.** When the rubric is specific and binary, the judge is a strong model, and it **agrees with human labels** on a sample (measure agreement; check position/verbosity bias). Check the judge by labeling ~50 outputs yourself and comparing; re-check when anything changes.
3. **Untrusted text.** Anything from users, documents, web pages, emails, tool results. Enumerate what the model can do with it (tools, output consumed by other systems) to see the blast radius of a successful injection.
