# How the planner chooses

A **cost-based** planner enumerates plans and picks the cheapest estimated one. Inputs: **table statistics** (row counts, per-column distinct values, most-common values, histograms), predicate **selectivity** estimates, and cost constants (`seq_page_cost = 1`, `random_page_cost = 4` by default, lower on SSDs; CPU costs per tuple).

| Plan                | Cheap when                                                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Seq scan**        | the query returns a large fraction of the table (roughly > 5-10%), or the table is small: reads pages sequentially |
| **Index scan**      | few rows match: a few random page reads beat reading everything                                                    |
| **Bitmap scan**     | medium selectivity: collect matching row ids from the index, fetch pages in order                                  |
| **Index-only scan** | the index covers all needed columns                                                                                |

So an index **doesn't always get used**, and that's correct. Wrong choices usually come from **stale or missing statistics** (`ANALYZE`), correlated columns, or non-sargable predicates (`WHERE lower(email) = ...` without a matching expression index; functions on the column).

An index speeds reads but **slows writes** (every insert/update maintains it) and uses space.

```sql
CREATE INDEX ON orders (customer_id);
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;   -- Seq Scan → Index Scan; 1M rows: ~100 ms → <1 ms
```

# Crash testing

Idea: **kill the process at random moments** and check invariants on restart.

```
writer:   loop { id = next(); put(k, v(id)); (after ack) append "acked id" to ack.log (separate durable file) }
killer:   sleep(random); kill -9 writer
verifier: reopen the store; check every acked write is present and readable; no corrupt values; store opens cleanly
```

Repeat thousands of times; also vary where it dies (use failpoints before/after `write`, `fsync`, `rename`). Typical bugs found: missing `fsync` of the file or directory, torn tail not truncated, replay not idempotent, rename-before-sync, index rebuilt from a partial record.

# Crash test harness (Python)

- Use `subprocess.Popen` to run your store as a child writer; the parent calls `proc.kill()` (SIGKILL) after a random delay.
- The child reports acknowledged ops over a pipe/file _after_ the store's fsync returns.
- Verifier opens the store and asserts: all acked present; values valid (checksum embedded in value); no extra "future" values.
- Loop 1000×; print the seed (`random.Random(seed)`), so a failing run can be replayed.

# Caches and the celebrity problem

**Celebrity** (everyone knows them, they know no one), with `knows(a, b)`: elimination in O(n) calls.

```python
c = 0
for i in range(1, n):
    if knows(c, i):
        c = i                                   # c knows i -> c can't be the celebrity
for i in range(n):
    if i != c and (knows(c, i) or not knows(i, c)):
        return -1                               # verify
return c
```

**LRU cache (O(1) get/put):** hash map `key → node` + doubly linked list ordered by recency (front = most recent). Python's `collections.OrderedDict` is exactly that pair:

```python
from collections import OrderedDict

class LRU:
    def __init__(self, cap: int) -> None:
        self.cap = cap
        self.d: OrderedDict[int, int] = OrderedDict()

    def get(self, k: int) -> int:
        if k not in self.d:
            return -1
        self.d.move_to_end(k)                   # most recent at the end
        return self.d[k]

    def put(self, k: int, v: int) -> None:
        if k in self.d:
            self.d.move_to_end(k)
        self.d[k] = v
        if len(self.d) > self.cap:
            self.d.popitem(last=False)          # evict the least recent
```

Write your own node-based version too (a dict plus a hand-built doubly linked list); that is what the interview asks for, and `functools.lru_cache` is the built-in version for function results.

**LFU cache (O(1)):** `key → node(value, freq)`, `freq → doubly linked list` of keys (LRU within a frequency), and a `minFreq` pointer. On access: move the key from list `f` to `f+1`; if list `f` empties and `f == minFreq`, `minFreq++`. On eviction: remove the LRU of `minFreq`.

**Number of greater elements to the right** (for each element): offline counting with a **Fenwick tree** over compressed values, scanning right→left, or merge sort.

# Chaos on purpose

Failures happen anyway; cause them deliberately, in a controlled way, to find weaknesses before users do.

1. Define **steady state** (metrics that mean "healthy").
2. Make a **hypothesis** ("if one replica dies, error rate stays < 1%").
3. **Inject** a fault: kill a process, drop packets, add latency, fill the disk, break a dependency.
4. Limit the **blast radius** and have an abort switch; start in test/staging.
5. Compare to steady state; fix what broke; automate and repeat.

Your crash test is chaos engineering in miniature. Tools: `kill -9`, `tc netem` (Linux latency/loss), Toxiproxy, Chaos Mesh.
