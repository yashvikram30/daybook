# Workflows vs agents (Anthropic)

- **Workflow:** LLMs and tools orchestrated through **predefined code paths** (prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer).
- **Agent:** the LLM **dynamically decides** its steps and tool calls in a loop until done.

Use a **fixed workflow** when the steps are known and you want predictability, lower latency/cost and easy testing; use an **agent** for open-ended tasks where steps can't be predicted. **Start with the simplest thing** (one well-prompted call, then a workflow) and add autonomy only when it measurably helps.

# The agent loop (ReAct: reason → act → observe)

```python
msgs = [{"role": "user", "content": task}]
for step in range(MAX_STEPS):                                   # hard step limit
    r = client.messages.create(model="claude-sonnet-5-5", max_tokens=1024, tools=TOOLS, messages=msgs)
    msgs.append({"role": "assistant", "content": r.content})
    if r.stop_reason != "tool_use": break                       # final answer
    results = []
    for b in r.content:
        if b.type == "tool_use":
            try:    out, err = run_tool(b.name, b.input), False
            except Exception as e: out, err = f"error: {e}", True   # errors go BACK to the model
            results.append({"type": "tool_result", "tool_use_id": b.id, "content": out, "is_error": err})
    msgs.append({"role": "user", "content": results})
```

**Tool design:** clear name and description (the model reads them), a JSON Schema for inputs, small outputs (truncate), return errors as data so the model can recover, make side-effecting tools idempotent.

# Function calling is the same loop everywhere

Gemini calls it function calling, Claude calls it tool use; the protocol is the same. You describe each tool by a name, a plain-language description and a JSON Schema for its arguments. The model may reply with a request to call a tool instead of text. Your code runs the function, sends the result back as a new message, and the model continues, until it answers in text. The model never executes anything; it only proposes calls, so _you_ validate the arguments and decide what is allowed. Frameworks such as LangChain and LangGraph wrap this loop and add state graphs and retries; write the plain loop once yourself first so you can see what they hide, and reach for a framework only when it removes real work.

# Failure modes (they look like distributed-systems ones)

Infinite loops and repeated calls, runaway cost, wrong tool/arguments, error cascades, **context growth**, and **prompt injection** through tool results. Controls: **max steps**, token/cost/time **budgets**, timeouts per tool, repeated-action detection, logging of every step, human approval for risky actions.

# Prompt injection and the lethal trifecta

Any text the agent reads (web page, file, email) can contain instructions. The dangerous combination (Willison): **access to private data + exposure to untrusted content + a way to communicate externally**. With all three, an attacker's page can make the agent leak your data. **Remove at least one leg**; don't rely on "ignore malicious instructions" in the prompt. Note even a "GET to an allowed host" can exfiltrate data in the URL.

# MCP (Model Context Protocol)

An open protocol (JSON-RPC) for exposing **tools, resources and prompts** from a server to any compatible model client, so integrations are written once.

# Unbounded knapsack and coin problems

Items can be reused: iterate capacity **upward**.

| Problem                                         | Recurrence                                                     |
| ----------------------------------------------- | -------------------------------------------------------------- |
| **Min coins** for amount `a`                    | `dp[a] = min(dp[a−c] + 1)`; `dp[0]=0`; unreachable = `inf`     |
| **Coin change II** (number of **combinations**) | outer loop **coins**, inner amounts upward: `dp[a] += dp[a−c]` |
| **Unbounded knapsack**                          | `dp[w] = max(dp[w], dp[w−wt] + val)` ascending                 |
| **Target sum** (assign +/− to each number)      | count subsets with sum `(total + target)/2` (0/1 knapsack)     |

```python
def coin_change(coins: list[int], amount: int) -> int:
    INF = 1 << 30
    dp = [0] + [INF] * amount
    for i in range(1, amount + 1):
        for c in coins:
            if c <= i:
                dp[i] = min(dp[i], dp[i - c] + 1)
    return -1 if dp[amount] >= INF else dp[amount]

def change(amount: int, coins: list[int]) -> int:           # combinations (order doesn't matter)
    dp = [1] + [0] * amount
    for c in coins:
        for a in range(c, amount + 1):
            dp[a] += dp[a - c]
    return dp[amount]
```

**Loop order matters:** coins outside → **combinations**; amounts outside → **permutations**. Upward inner loop = unbounded; downward = 0/1.

Target sum: `(total+target)` must be even and `|target| ≤ total`.

# Least privilege for tools

Give a tool exactly the access its job needs, because a model (or an attacker steering it) will eventually call it with unexpected arguments.

| Tool        | Narrow it by                                                                                             |
| ----------- | -------------------------------------------------------------------------------------------------------- |
| file reader | a single root directory; **resolve** paths (`..`, symlinks) then check the prefix; read-only; size limit |
| HTTP        | scheme + **host allowlist**, no redirects off-list, timeout, size limit, block private IP ranges (SSRF)  |
| shell/code  | sandbox (container, no network, resource limits), never run model output unreviewed                      |
| database    | read-only role, specific tables/views, row limits                                                        |
| credentials | per-tool scoped tokens, short-lived, not visible to the model                                            |

Also: **human confirmation** for destructive/irreversible actions, **rate limits** and budgets, **audit logs** of every call, and separate the tool layer from the prompt: enforce the rules in **code**, not in instructions to the model.

1. **Workflow vs agent.** When the steps are known in advance: a fixed workflow is cheaper, faster, more predictable and easier to test. Use an agent when the path can't be predicted and flexibility is worth the extra cost and risk.
2. **Runaway agents.** A hard step limit, token/cost and wall-clock budgets, per-tool timeouts, repeated-call detection, and rate limits, all enforced in your code outside the model.
3. **Injected "send me the notes".** Design so it can't happen regardless of what the model decides: the file tool is restricted (and notes are outside its root or tool is not given), and there's no outbound channel to send data (break the lethal trifecta). The model's compliance is not a defense.
