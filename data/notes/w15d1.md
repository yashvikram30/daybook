# Embeddings

An **embedding model** maps text (or images…) to a **dense vector** (e.g. 384-3072 dimensions) so that things with **similar meaning/use are close together**. Search becomes: embed the query, find the nearest document vectors.

```python
from sentence_transformers import SentenceTransformer
import numpy as np
m = SentenceTransformer("all-MiniLM-L6-v2")                  # 384-dimensional
E = m.encode(chunks, normalize_embeddings=True)               # (N, 384), unit length
q = m.encode([query], normalize_embeddings=True)[0]
top = np.argsort(-(E @ q))[:10]                               # exact top-10 by cosine
```

# Similarity measures

| Measure        | Formula          | Notes                                                                                                                                 |
| -------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Cosine**     | `a·b / (‖a‖‖b‖)` | angle between vectors; ignores length; the default for text                                                                           |
| Dot product    | `a·b`            | same ranking as cosine **if vectors are unit-length**; use it when magnitude carries signal (some models are trained for dot product) |
| Euclidean (L2) | `‖a−b‖`          | for unit vectors, `‖a−b‖² = 2 − 2cos`, so the ranking is the same                                                                     |

Follow the model's documentation for which metric it was trained for.

# Why exact search doesn't scale

Exact k-NN compares the query with **every** vector: `O(N·d)` per query. 10 M vectors × 768 dims ≈ 7.7 G multiply-adds per query: too slow for low latency and high QPS. **Approximate nearest neighbor (ANN)** indexes trade accuracy for speed:

| Index    | Idea                                                                                                                                                                                                                                           |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **HNSW** | layered proximity graph, a **skip list over a graph**: greedy-walk from a sparse top layer down to the dense bottom layer; knobs `M` (links per node), `efConstruction`, **`ef_search`** (candidates explored: higher = better recall, slower) |
| IVF      | cluster the vectors; search only the `nprobe` nearest clusters                                                                                                                                                                                 |
| PQ       | compress vectors into short codes to save memory                                                                                                                                                                                               |

**What you give up:** **exactness** (may miss true neighbors: measure **recall@k** vs exact), build time and memory (HNSW lives in RAM), harder deletes/updates, more tuning. Contrast with a B-tree: exact, one-dimensional ordered keys, disk-friendly; vector indexes are approximate and high-dimensional.

# Why opposite meanings can embed close

Embeddings capture **topical/contextual similarity**: "The food was great" and "The food was terrible" share topic, structure and words, and words like _great/terrible_ appear in the same contexts. Models are trained for relevance/paraphrase, not logical contradiction, so **negation and antonyms are weak spots**; that's one reason to rerank and to use keyword search too.

# DP on two strings (LCS family)

`dp[i][j]` over prefixes `s[:i]`, `t[:j]`.

| Problem                                         | Recurrence                                                                                  |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **Longest common substring** (contiguous)       | `dp[i][j] = dp[i-1][j-1] + 1` if `s[i-1]==t[j-1]` else **`0`**; answer = max over all cells |
| **Longest palindromic subsequence**             | `LCS(s, reverse(s))` (or interval DP)                                                       |
| **Min insertions to make a palindrome**         | `n − LPS(s)`                                                                                |
| **Min insertions + deletions to turn A into B** | `len(A) + len(B) − 2·LCS(A, B)`                                                             |

```python
def longest_common_substring(s: str, t: str) -> int:
    dp = [[0] * (len(t) + 1) for _ in range(len(s) + 1)]
    best = 0
    for i in range(1, len(s) + 1):
        for j in range(1, len(t) + 1):
            if s[i - 1] == t[j - 1]:
                dp[i][j] = dp[i - 1][j - 1] + 1
                best = max(best, dp[i][j])          # else stays 0
    return best

def lps(s: str) -> int:
    return lcs(s, s[::-1])
```

**Substring vs subsequence:** substring resets to 0 on mismatch; subsequence carries `max(dp[i-1][j], dp[i][j-1])`.

Time O(mn), space O(mn) (O(n) with a rolling row).

# Benchmark as a curve, not a number

Approximate systems trade **quality for speed**, so a single number is meaningless ("1,000 QPS" at what recall?).

- Sweep the knob (`ef_search`, `nprobe`) and plot **quality vs cost**: recall@k on the y-axis, QPS or p95 latency on the x-axis. The **Pareto frontier** is the result; compare indexes by whether their curve is above/left.
- Report: dataset (size, dimension), hardware, threads, batch size, **build time**, **memory**, recall definition (vs exact), `k`, warm-up, percentile latencies.
- Fix everything else; one variable at a time; repeat runs and show variance.
- ANN-Benchmarks does this and is a good template.
