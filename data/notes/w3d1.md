# Process = running program + its resources

A process has its own **virtual address space**, registers/PC, **file-descriptor table**, pid, credentials, working directory, environment. The kernel tracks it in a process control block. States: **running → ready ↔ blocked**, and **zombie** after exit until the parent reaps it.

# System calls

User code can't touch hardware; it traps into the kernel: put the syscall number and args in registers, execute `svc` (arm64) / `syscall` (x86-64), kernel runs in privileged mode, returns a result or `-errno`. Libraries wrap this: in Python, the `os`, `socket` and `select` modules call the operating system's library for you. Each is a mode switch (hundreds of ns), so batching I/O helps.

# fork / exec / wait

| Call               | Effect                                                                                 |
| ------------------ | -------------------------------------------------------------------------------------- |
| `fork()`           | clones the process; returns **twice**: child pid in the parent, `0` in the child       |
| `exec*()`          | replaces the current program image; **same pid, same open fds** (unless close-on-exec) |
| `wait()/waitpid()` | parent blocks for a child to exit and **reaps** it (collects status)                   |
| `exit()`           | terminate; becomes zombie until waited                                                 |

```python
import os

pid = os.fork()
if pid == 0:
    os.execlp("ls", "ls", "-l")   # child; only returns by raising if exec fails
else:
    os.waitpid(pid, 0)            # parent
```

**Copy-on-write:** fork copies page _tables_, not memory; pages are shared read-only and copied only when either side writes. This makes fork cheap, and fork+exec doesn't waste the copy.

**Why separate fork and exec?** Between them the child can rearrange fds (redirect, pipe), set env, dir, process group, then exec. This is how shells implement `>` and `|`.

# In Python

```python
import subprocess

r = subprocess.run(["ls", "-l"], capture_output=True, text=True)   # fork+exec+wait
print(r.returncode, r.stdout)
p = subprocess.Popen(["ls", "-l"])                                   # p.pid, p.wait()
```

The `os` module also exposes the raw calls, so you can write the raw fork/exec/wait sequence almost line for line:

```python
import os

pid = os.fork()
if pid == 0:                                  # child
    try:
        os.execvp("ls", ["ls", "-l"])
    finally:
        os._exit(127)                         # only reached if exec fails
else:
    os.waitpid(pid, 0)                        # parent
```

`os.fork` is the real `fork`, but it is dangerous in a program with threads: the child keeps **only the calling thread**, and any lock another thread held at that moment stays locked forever in the child. Python 3.12 and later emit a `DeprecationWarning` when you fork a multithreaded process. `subprocess` avoids the problem by doing the fork and exec together in carefully written native code. Use `os._exit` (not `sys.exit`) in a forked child so the parent's cleanup handlers and buffered output are not run twice.

# strace

`strace -f ./prog` traces syscalls (`-f` follows children). Look for `clone`, `execve`, `openat`, `read`, `write`, `exit_group`.

# Sum problems

**Two Sum** (return indices): one pass with a map `value → index`; for each `v`, look up `target - v` _before_ inserting `v`. O(n).

```python
def two_sum(a: list[int], t: int) -> list[int]:
    seen: dict[int, int] = {}
    for i, v in enumerate(a):
        if t - v in seen:
            return [seen[t - v], i]
        seen[v] = i
    return []
```

**3Sum / 4Sum** (unique tuples): **sort**, fix one (or two) elements, then **two pointers** on the rest; skip duplicates at every level.

```python
a.sort()
res = []
n = len(a)
for i in range(n - 2):
    if i > 0 and a[i] == a[i - 1]:
        continue
    l, r = i + 1, n - 1
    while l < r:
        s = a[i] + a[l] + a[r]
        if s < 0:
            l += 1
        elif s > 0:
            r -= 1
        else:
            res.append([a[i], a[l], a[r]])
            while l < r and a[l] == a[l + 1]:
                l += 1
            while l < r and a[r] == a[r - 1]:
                r -= 1
            l += 1
            r -= 1
```

| Problem       | Time  | Space      |
| ------------- | ----- | ---------- |
| Two Sum (map) | O(n)  | O(n)       |
| 3Sum          | O(n²) | O(1) extra |
| 4Sum          | O(n³) | O(1) extra |

4Sum: Python ints cannot overflow, so there is nothing to guard against; in Java or C++ sum four values in a 64-bit type.

**Dutch national flag (sort 0/1/2), one pass, O(1):** `lo`, `mid`, `hi`.

```python
lo, mid, hi = 0, 0, len(a) - 1
while mid <= hi:
    if a[mid] == 0:
        a[lo], a[mid] = a[mid], a[lo]
        lo += 1
        mid += 1
    elif a[mid] == 1:
        mid += 1
    else:
        a[mid], a[hi] = a[hi], a[mid]
        hi -= 1                       # do not advance mid
```

1. **What fork copies.** The process's address space (via copy-on-write page-table copies), registers, fd table (entries point to the _same_ open file descriptions, so file offsets are shared), signal dispositions, env, cwd. COW is needed because copying all memory eagerly is slow and wasteful, especially when the child immediately calls exec.
2. **Why fork/exec are separate.** The window between them lets the child change its own fds, env, cwd, process group _before_ becoming the new program. A shell uses it to implement redirection and pipes without the target program knowing.
3. **Fork and threads.** A multithreaded process has several OS threads (in Python, also the threads that hold the GIL or other locks). `fork` duplicates only the calling thread; the child inherits copies of every lock in whatever state it was in, with no thread left to release them. A lock held by another thread at the moment of the fork is held forever in the child, so the child can deadlock. That is why Python 3.12 warns about it, and why `subprocess` does fork and exec together.
