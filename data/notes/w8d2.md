# Running Postgres in Docker

A **container** is an ordinary process that the kernel isolates with its own view of the filesystem, network and process list. It is not a virtual machine; it shares the host kernel, so it starts in milliseconds. An **image** is the read-only layered template a container starts from; a **volume** is storage that outlives the container.

```
docker run --name pg -e POSTGRES_PASSWORD=dev -p 5432:5432 \
           -v pgdata:/var/lib/postgresql/data -d postgres:17
psql -h localhost -U postgres          # or psycopg.connect("postgresql://postgres:dev@localhost/postgres")
docker stop pg && docker start pg      # data survives because of the volume
```

`-p 5432:5432` publishes the container's port on your machine; `-e` sets an environment variable the image reads on first start. Without the volume, removing the container deletes the data.

# Serializability

A **schedule** is an interleaving of the operations of several transactions. A **serial** schedule runs one transaction at a time, which is always correct but slow. A schedule is **serializable** if its effect equals some serial order. The practical test is **conflict serializability**:

- Two operations **conflict** if they come from different transactions, touch the same item, and at least one is a write.
- Draw the **precedence graph**: one node per transaction, and an edge `Ti → Tj` whenever an operation of `Ti` conflicts with a _later_ operation of `Tj`.
- The schedule is conflict serializable **if and only if the graph has no cycle**; a topological order of the graph is an equivalent serial order.

Example: `r1(A) w2(A) w1(A)` has `T1 → T2` (read before write) and `T2 → T1` (write before write), a cycle, so it is not serializable. It is exactly the lost-update pattern.

**Recoverability** is a separate concern: a schedule is _recoverable_ if a transaction commits only after every transaction it read from has committed. Otherwise an abort would leave a committed transaction that used data that never existed. If one abort forces others to abort too, that is a **cascading rollback**; schedules where transactions read only committed data (**avoid cascading aborts**) and ones that also never overwrite uncommitted data (**strict**) are the safe ones, and strict two-phase locking produces them.

# Anomalies

| Anomaly                 | What happens                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------- |
| **Dirty read**          | read another transaction's _uncommitted_ write                                     |
| **Non-repeatable read** | read a row twice, value changed in between (other tx committed)                    |
| **Phantom**             | re-run a range query, new rows appear                                              |
| **Lost update**         | two read-modify-write cycles; one overwrites the other                             |
| **Read skew**           | see parts of two different states (e.g. one account debited, not yet credited)     |
| **Write skew**          | two txs read the same data, write _different_ rows, jointly violating an invariant |

# Isolation levels (SQL standard) and what they allow

| Level            | Dirty read | Non-repeatable | Phantom        |
| ---------------- | ---------- | -------------- | -------------- |
| Read uncommitted | possible   | possible       | possible       |
| Read committed   | no         | possible       | possible       |
| Repeatable read  | no         | no             | possible (std) |
| Serializable     | no         | no             | no             |

The standard's definitions are loose (see the _Critique_ paper). **Real behaviour:**

- **PostgreSQL:** READ UNCOMMITTED = READ COMMITTED (default). REPEATABLE READ = **snapshot isolation** (no phantoms, but **write skew** possible, concurrent-update conflicts error). SERIALIZABLE = SSI: aborts with SQLSTATE `40001` "could not serialize access", so **apps must retry**.
- **MySQL/InnoDB:** default REPEATABLE READ (snapshot reads + gap locks).

**Snapshot isolation allows write skew; serializable does not.**

# Write-skew example (on-call doctors; rule: ≥ 1 on call)

```
T1: BEGIN; SELECT count(*) FROM oncall WHERE on_duty;   -- 2
T2: BEGIN; SELECT count(*) FROM oncall WHERE on_duty;   -- 2
T1: UPDATE oncall SET on_duty=false WHERE name='alice'; COMMIT;
T2: UPDATE oncall SET on_duty=false WHERE name='bob';   COMMIT;   -- nobody on call!
```

# Lost update and fixes

`x = read(); write(x+1)` in two sessions loses one increment. Fixes: atomic `UPDATE t SET n = n + 1`, `SELECT ... FOR UPDATE`, compare-and-set (version column), or REPEATABLE READ/SERIALIZABLE (+ retry).

# Why not serializable by default?

Weaker levels block/abort less and run faster; most workloads tolerate their anomalies; serializable needs retry logic and costs throughput (locks or conflict tracking).

# Monotonic stack and deque

**Next smaller element:** same as next greater with the opposite comparison; scan right→left, pop while `top >= a[i]`.

**Remove K digits (smallest number):** keep an **increasing** stack; while `k > 0` and top `>` current digit, pop (a larger digit before a smaller one is wasteful). Afterwards drop remaining `k` from the end, strip leading zeros, return `"0"` if empty.

```python
st: list[str] = []
for c in num:
    while k > 0 and st and st[-1] > c:
        st.pop()
        k -= 1
    st.append(c)
st = st[:len(st) - k] if k else st
```

**Min stack:** every entry stores `(value, minSoFar)`, or keep a second stack of minima. `push/pop/top/getMin` in O(1).

**Sliding window maximum:** deque of **indices** whose values are decreasing; the front is the max.

```python
from collections import deque

dq: deque[int] = deque()                       # indices, values decreasing
res = []
for i, v in enumerate(a):
    while dq and a[dq[-1]] <= v:
        dq.pop()                               # drop smaller from back
    dq.append(i)
    if dq[0] <= i - k:
        dq.popleft()                           # front out of window
    if i >= k - 1:
        res.append(a[dq[0]])
```

O(n): each index enters and leaves once.

# Reproduce before you fix

A bug you can't reproduce is a bug you can't confirm fixed.

1. **Capture** the exact inputs, environment, version, logs.
2. **Reduce** to a minimal reproduction (delete code/inputs until it still fails). Use `git bisect` to find the commit that introduced it.
3. Turn it into a **failing test** (or script).
4. Form a hypothesis, check it with logs or a debugger, fix, see the test pass, keep the test.
5. For concurrency bugs: make the interleaving deterministic (inject sleeps or hooks, lower `sys.setswitchinterval`, repeat the test many times).

Reading logs: filter by request/transaction id, order by timestamp, look for the _first_ anomaly, not the loudest one.

1. **Snapshot isolation vs serializable.** Write skew (and some other multi-row anomalies): two transactions read overlapping data and write disjoint rows, each valid on its own snapshot but violating an invariant together. Serializable prevents it (by locking or SSI aborting one).
2. **Weaker default.** Higher concurrency and throughput, fewer blocks/aborts and no need for retry loops; most apps are fine with read committed or snapshot isolation, and stronger levels are opt-in where needed.
3. **Precedence graph test.** Draw one node per transaction. For each pair of **conflicting** operations (different transactions, same item, at least one a write), add an edge from the transaction whose operation comes first to the other. The schedule is **conflict serializable if and only if the graph has no cycle**; any topological order of the graph is an equivalent serial schedule. A cycle (for example `T1 → T2` from `r1(A) w2(A)` and `T2 → T1` from `w2(A) w1(A)`) means no serial order matches, as in a lost update.
