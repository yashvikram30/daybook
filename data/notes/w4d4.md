# Files and inodes

- An **inode** stores metadata (size, owner, permissions, timestamps, link count, block pointers). It does **not** store the name.
- A **directory** is a file mapping _names → inode numbers_.
- **Hard link:** another directory entry for the **same inode** (link count++); same filesystem only; file is freed when count = 0 and no open fds.
- **Symlink:** a small file containing a _path_; has its own inode; can cross filesystems and **dangle**.

```
$ ls -i a.txt ; ln a.txt hard ; ln -s a.txt soft ; stat a.txt   # Links: 2
```

# Disk access time and disk scheduling

A hard disk read costs **seek time** (move the arm to the right track) + **rotational latency** (wait for the sector to come around; on average half a turn, about 4.2 ms at 7200 RPM) + **transfer time** (usually tiny). Seek dominates, so the order in which queued requests are served matters. SSDs have no arm, so these algorithms matter only for spinning disks, but the ideas recur wherever a resource has a "position".

Head at cylinder 53, queue `98 183 37 122 14 124 65 67`, cylinders 0 to 199:

| Algorithm           | Rule                                                      | Head movement                 |
| ------------------- | --------------------------------------------------------- | ----------------------------- |
| **FCFS**            | in arrival order                                          | 640                           |
| **SSTF**            | closest request next                                      | 236 (can starve far requests) |
| **SCAN** (elevator) | sweep one way to the end, then reverse                    | 236 (going down first)        |
| **C-SCAN**          | sweep one way, jump back to the start, sweep again        | 382 (more uniform waiting)    |
| **LOOK**            | like SCAN but turn at the last request, not the disk edge | 208                           |
| **C-LOOK**          | like C-SCAN with the same shortcut                        | 322                           |

# How files are laid out

| Allocation     | How blocks are found                | Good at                           | Bad at                                                         |
| -------------- | ----------------------------------- | --------------------------------- | -------------------------------------------------------------- |
| **Contiguous** | start block + length                | fast sequential and random access | external fragmentation, hard to grow                           |
| **Linked**     | each block points to the next       | no fragmentation, easy growth     | random access walks the chain; one lost pointer loses the rest |
| **Indexed**    | an index block lists all the blocks | random access, no fragmentation   | the index block is overhead for tiny files                     |

The Unix **inode** is indexed allocation with a twist: it holds about 12 _direct_ pointers, then one _single-indirect_ pointer (to a block of pointers), one _double-indirect_ and one _triple-indirect_. With 4 KiB blocks and 4-byte pointers, a block holds 1024 pointers, so the maximum file size is (12 + 1024 + 1024² + 1024³) × 4 KiB, about 4 TiB. Small files, which are the common case, need no indirection at all.

# Writes aren't durable by default

`write()` copies into the **page cache** and returns. The kernel flushes later. A crash/power loss can lose it.

| Call                               | Guarantees                                                                          |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| `write`                            | in OS cache only                                                                    |
| `os.fsync(fd)` (after `f.flush()`) | file data + metadata handed to the device (and device cache flushed, where honored) |
| fsync of the **directory**         | a newly created/renamed file's _name_ is durable                                    |

Caveats: disks/firmware may lie about flushes; macOS needs `F_FULLFSYNC`, which Python's `os.fsync` does not issue by itself (use `fcntl.fcntl(fd, fcntl.F_FULLFSYNC)`); an fsync error may be reported once and the dirty pages dropped. `os.write` can also be **partial**, so check the count it returns. Python's buffered `file.write` keeps data in a **user-space buffer** first, so the full chain is `f.write(...)`, `f.flush()`, then `os.fsync(f.fileno())`.

Safe replace pattern: write temp file → `fsync` → `os.replace` over target → `fsync` directory (rename is atomic).

```python
import os

def atomic_write(path: str, data: bytes) -> None:
    tmp = path + ".tmp"
    with open(tmp, "wb") as f:
        f.write(data)
        f.flush()
        os.fsync(f.fileno())
    os.replace(tmp, path)
    d = os.open(os.path.dirname(path) or ".", os.O_RDONLY)
    try:
        os.fsync(d)                     # make the new name durable
    finally:
        os.close(d)
```

# Crash consistency

One logical update touches several blocks (inode, bitmap, data). A crash between them leaves the filesystem inconsistent. **fsck** scans the entire disk to repair (slow). **Journaling** (write-ahead logging):

```
1. journal write : TxBegin + blocks to be written     (to the journal)
2. journal commit: TxEnd  (after 1 is durable)        <- transaction is now committed
3. checkpoint    : write blocks to their real location
4. free journal space
```

**Recovery:** replay committed transactions from the journal; ignore incomplete ones. Cost is proportional to the journal, not the disk. _Metadata (ordered) journaling_ writes data first, then journals metadata only (faster, common default); _data journaling_ logs data too.

# Checksummed log record

`[len u32][crc32 u32][payload]`, packed with `struct.pack("<II", len(p), zlib.crc32(p)) + p`. On recovery read records until the length/checksum is invalid, then truncate: that is a **torn write** from a crash.

```python
import struct, zlib

def append(f, p: bytes) -> None:
    f.write(struct.pack("<II", len(p), zlib.crc32(p)) + p)
    f.flush()
    os.fsync(f.fileno())

def recover(f) -> list[bytes]:
    good, out = 0, []
    while len(head := f.read(8)) == 8:
        n, crc = struct.unpack("<II", head)
        p = f.read(n)
        if len(p) < n or zlib.crc32(p) != crc:
            break                       # torn write: stop here
        out.append(p)
        good = f.tell()
    f.truncate(good)                    # drop the torn tail
    return out
```

# More binary search on the answer

**Aggressive cows** (maximize the minimum distance): sort stalls; `feasible(d)` = greedily place cows at least `d` apart, count ≥ k. Search `d` in `[1, max-min]` for the **largest** feasible `d`.

```python
lo, hi = 1, st[-1] - st[0]
while lo < hi:
    mid = lo + (hi - lo + 1) // 2      # upper mid: we are moving lo up
    if can_place(st, k, mid):
        lo = mid
    else:
        hi = mid - 1
```

**Book allocation / painter's partition** (minimize the maximum load): `feasible(x)` = greedy split into ≤ K parts each ≤ x; range `[max, Σ]`.

**Peak element** (`a[i] > neighbors`): compare `a[mid]` and `a[mid+1]`; move toward the larger side, which must contain a peak. O(log n).

```python
lo, hi = 0, len(a) - 1
while lo < hi:
    mid = lo + (hi - lo) // 2
    if a[mid] < a[mid + 1]:
        lo = mid + 1
    else:
        hi = mid
```

**Median of two sorted arrays**, O(log(min(m,n))): binary search a partition `i` of the smaller array, `j = (m+n+1)/2 - i` of the other, until `maxLeft ≤ minRight` on both sides.

```python
def median(a: list[int], b: list[int]) -> float:
    if len(a) > len(b):
        a, b = b, a
    m, n = len(a), len(b)
    lo, hi = 0, m
    while lo <= hi:
        i = (lo + hi) // 2
        j = (m + n + 1) // 2 - i
        a_l = a[i - 1] if i > 0 else float("-inf")
        a_r = a[i] if i < m else float("inf")
        b_l = b[j - 1] if j > 0 else float("-inf")
        b_r = b[j] if j < n else float("inf")
        if a_l <= b_r and b_l <= a_r:
            if (m + n) % 2 == 1:
                return float(max(a_l, b_l))
            return (max(a_l, b_l) + min(a_r, b_r)) / 2
        if a_l > b_r:
            hi = i - 1
        else:
            lo = i + 1
    raise ValueError("inputs must be sorted")
```

When maximizing, use the **upper mid** (`lo + (hi-lo+1)/2`) or the loop never terminates.

# Why durability matters for your database

The **D** in ACID: once a transaction is acknowledged as committed, it must survive a crash. That requires:

1. Write the change to a **log** (WAL) first, sequentially.
2. **`fsync`** the log before replying "committed".
3. Update the main data later; on recovery, **replay the log**.

Without fsync, "committed" data may exist only in RAM. With fsync on every commit, throughput is bounded by fsync latency, so databases use **group commit** (many transactions share one fsync). Weeks 7-8 build exactly this.

1. **fsync.** It forces the file's dirty data and metadata to the storage device and waits. Still possible: the directory entry not durable (need to fsync the directory), hardware cache lying about flushes, a reported fsync error with data already dropped, earlier partial writes, and corruption not detected without checksums.
2. **Journal recovery.** Every change is first written to the journal as a transaction ending in a commit record. After a crash, the filesystem reads the small journal, replays committed transactions (redo) and discards incomplete ones, so it doesn't have to scan the whole disk.
3. **SSTF, SCAN and inodes.** **SSTF** always serves the closest request, so while new requests keep arriving near the head, a request at the far edge is never the closest and waits indefinitely (starvation). **SCAN** (the elevator) sweeps in one direction serving everything on the way and then reverses, so every request is reached within two sweeps. **C-SCAN** sweeps only one way and jumps back, so the wait time is more uniform because cylinders at the edges are not visited twice as often as those in the middle. Inode capacity: 12 direct pointers address 12 blocks; one single-indirect pointer points to a block of pointers, so with 4 KiB blocks and 4-byte pointers it adds 1024 more, for 12 + 1024 = 1036 blocks, about 4.05 MiB. (The answer scales with block and pointer size.)
