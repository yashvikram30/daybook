# Two phases of generation

| Phase       | What happens                                                               | Bound by                                                                 | Metric                                    |
| ----------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------- |
| **Prefill** | process the whole prompt **in parallel**; produces the first token         | **compute** (big matrix multiplies)                                      | time to first token (**TTFT**)            |
| **Decode**  | generate **one token at a time**; each step needs the weights and KV cache | **memory bandwidth** (reads all weights per token for little arithmetic) | time per output token / tokens per second |

So the first token is slower (it pays for the entire prompt). Rule of thumb for decode at batch 1: **tokens/s ≈ memory bandwidth ÷ bytes read per token** (≈ model size). A 7B model in fp16 (≈ 14 GB) on 100 GB/s memory ≈ 7 tok/s; 4-bit (≈ 4 GB) ≈ 25 tok/s. Batching many requests amortizes the weight reads (higher throughput).

# KV cache

Without caching, each new token would recompute keys/values for all previous tokens. Store `K` and `V` per layer for every past token instead:

`KV bytes = 2 (K and V) × layers × kv_heads × head_dim × tokens × bytes_per_value × batch`

Example: Llama-2-7B (32 layers, 32 KV heads, head_dim 128, fp16): `2·32·32·128·2 B = 512 KB/token` → **2 GB for 4,096 tokens** per sequence. **GQA** (grouped-query attention, fewer KV heads; Llama-3-8B has 8) cuts this ~4×. The cache **grows linearly with context** and competes with weights for memory.

# PagedAttention (vLLM) ≈ virtual memory

Reserving one contiguous maximum-length KV buffer per request wastes memory (fragmentation, over-reservation). PagedAttention stores the cache in **fixed-size blocks** at **non-contiguous** physical locations with a **block table** mapping logical → physical (just like **page tables**), allocating on demand and **sharing prefix blocks** copy-on-write. Result: far less waste → larger batches → higher throughput.

# Quantization

Store weights in **int8/int4** (e.g. GGUF `Q4_K_M`, GPTQ, AWQ) instead of fp16/bf16: ~2-4× less memory and faster decode (since it's bandwidth-bound), at some **quality loss** (small for large models at 8-bit; larger at 4-bit and below, in small models, math/code, long contexts). **Check on your task:** run the same prompts and metric on the fp16 and quantized model and compare accuracy and latency; don't trust perplexity alone.

# Measurement plan

1. Models: one 1-3B model at two quantizations (e.g. `Q4_K_M` and `Q8_0`/fp16). Prompt lengths ~50, ~500, ~2,000 tokens; fixed output length (e.g. 128 tokens, temperature 0).

3. **KV estimate:** read `n_layers`, `n_kv_heads`, `head_dim` from the model config; compute bytes/token and × context; compare with the extra memory you observe (Activity Monitor / `ollama ps`).
4. **Table:** model × quant × prompt length → TTFT (median, p95), tok/s, memory.
5. **Conclusion:** short prompts: TTFT small, total time dominated by **decode** (memory-bound, ∝ output tokens). Long prompts: **prefill** (compute-bound, ∝ prompt length) and KV-cache memory dominate. Quantization speeds decode roughly in proportion to bytes read.

# Knapsack-style DP

**Subset sum (is there a subset with sum = target?):** boolean DP over sums; iterate sums **downward** so each item is used at most once (0/1).

```python
def subset_sum(a: list[int], target: int) -> bool:
    dp = [False] * (target + 1)
    dp[0] = True
    for v in a:
        for s in range(target, v - 1, -1):        # downward: each item used at most once
            dp[s] = dp[s] or dp[s - v]
    return dp[target]
```

**Partition equal subset sum:** total must be even; ask for a subset with sum `total/2`.

**Stock with cooldown** (states):

```python
hold, sold, rest = -prices[0], 0, 0
for p in prices[1:]:
    hold, sold, rest = max(hold, rest - p), hold + p, max(rest, sold)
return max(sold, rest)
```

**Stock with fee:** see the previous day.

Time O(n·target), space O(target). Direction of the inner loop is the 0/1 (downward) vs unbounded (upward) distinction (next days).

# Report latency honestly

- Use **percentiles** (p50, p95, p99) and **max**, not just the mean: averages hide the slow tail users feel.
- State **how** you measured: client or server side, warm-up discarded, number of runs, concurrency, prompt/output lengths, model + quantization + hardware + software versions, temperature.
- Separate **TTFT** from **per-token** speed; report throughput (tok/s) _and_ latency, since batching trades one for the other.
- Beware **coordinated omission** (a closed-loop load generator that waits stops sending during stalls and hides them), cold starts, and thermal throttling on laptops.
- Show variance (min/median/p95 over ≥ 5 runs), don't cherry-pick the best run, and publish the script.

```python
import statistics as st
qs = st.quantiles(times, n=100); print(f"p50={st.median(times):.2f}s p95={qs[94]:.2f}s p99={qs[98]:.2f}s (n={len(times)})")
```

1. **Slow first token.** The first token requires **prefill**: running the entire prompt through the model, which is **compute-bound** (large parallel matrix multiplications). Later tokens use the **decode** phase: one token at a time, **memory-bandwidth-bound** (read all weights and the KV cache per token).
2. **KV cache growth.** It holds K and V for every previous token in every layer, so size is linear in context length (and batch size). PagedAttention manages it like virtual memory: fixed-size blocks, a block table from logical to physical blocks, on-demand allocation and shared prefixes, avoiding fragmentation.
3. **Quantization.** You lose numerical precision, which can degrade accuracy (more at 4-bit, in small models, on math/code/long context). Check by running the same eval set and prompts on both models and comparing task accuracy and latency.
