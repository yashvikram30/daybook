# Condition variable

Lets a thread sleep **until a condition becomes true**, without spinning. `wait()` atomically releases the lock and sleeps; on wake-up it re-acquires the lock. `notify()` wakes one waiter, `notify_all()` wakes all.

**Always wait in a loop:** wake-ups can be spurious, and another thread may have changed the state before you reacquire the lock (Mesa semantics).

```python
import threading
from collections import deque

class Buffer:
    def __init__(self, cap: int) -> None:
        self._q: deque[int] = deque()
        self._cap = cap
        self._lock = threading.Lock()
        self._not_empty = threading.Condition(self._lock)   # two conditions, one lock
        self._not_full = threading.Condition(self._lock)

    def put(self, v: int) -> None:
        with self._lock:
            while len(self._q) == self._cap:     # while, not if
                self._not_full.wait()
            self._q.append(v)
            self._not_empty.notify()

    def get(self) -> int:
        with self._lock:
            while not self._q:
                self._not_empty.wait()
            v = self._q.popleft()
            self._not_full.notify()
            return v
```

`Condition.wait_for(predicate)` runs that loop for you. In idiomatic Python the same thing is a **`queue.Queue(maxsize=cap)`** (which is built from exactly this lock and these conditions), or an `asyncio.Queue` in async code.

# Semaphore

A counter with `wait` (decrement, block at 0) and `post` (increment). Initial 1 = a lock; initial N = at most N concurrent users. In Python: `threading.Semaphore(n)` used as `with sem:` (or `asyncio.Semaphore` in async code).

# Classic synchronization problems

**Bounded buffer (producer and consumer).** Three semaphores: `empty` (free slots, starts at N), `full` (filled slots, starts at 0) and a `mutex` (starts at 1) around the buffer itself.

```python
import threading
from collections import deque

N = 8
buf: deque[int] = deque()
empty, full, mutex = threading.Semaphore(N), threading.Semaphore(0), threading.Lock()

def producer(item: int) -> None:
    empty.acquire()               # wait for a free slot
    with mutex:
        buf.append(item)
    full.release()                # announce one more item

def consumer() -> int:
    full.acquire()                # wait for an item
    with mutex:
        item = buf.popleft()
    empty.release()
    return item
```

Order matters: taking `mutex` before `empty` can deadlock, because a producer would sleep on `empty` while holding the lock the consumer needs.

**Readers and writers.** Many readers may share the data, but a writer needs it alone. The simple version (readers first) lets readers keep arriving so a writer **starves**; the fair version queues new readers behind a waiting writer. Python offers no read-write lock in the standard library, so you build one from a `Condition`, or use a plain `Lock` when reads are short.

**Dining philosophers.** Five philosophers, five forks, each needs both neighbours' forks. If all pick up their left fork at once, nobody can pick up the right: deadlock. Fixes: number the forks and always take the lower one first (breaks circular wait), allow at most four to sit, or pick up both forks atomically.

**Monitors.** A monitor bundles shared data with the lock and condition variables that guard it, so callers cannot forget to lock. A Python class that holds a `threading.Condition` and does everything inside `with self._cond:` is a monitor; the `Buffer` above is one.

# Deadlock: Coffman's four conditions (all needed)

1. **Mutual exclusion** 2. **Hold and wait** 3. **No preemption** 4. **Circular wait**

Break any one. **Lock ordering** (always acquire locks in a global order) breaks circular wait. Dining philosophers: each takes left fork then right → all hold one and wait. Fix: order forks by number.

Python does not detect deadlock at all: the program just hangs. To find the stuck threads, call `faulthandler.dump_traceback_later(10, exit=True)` early in the program, or run `py-spy dump --pid <pid>` against the hung process. `lock.acquire(timeout=...)` turns a silent hang into an error you can handle.

# Deadlock: handling it

| Approach                   | Idea                                                                                                     | Cost                                         |
| -------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| **Prevention**             | make one of the four conditions impossible (lock ordering, request everything at once, allow preemption) | restrictive, lower utilisation               |
| **Avoidance**              | grant a request only if the system stays in a _safe state_                                               | needs each process's maximum demand up front |
| **Detection and recovery** | let deadlock happen, find it, then break it                                                              | detection cost, lost work on recovery        |
| **Ignore it**              | the "ostrich" approach most general-purpose systems take                                                 | deadlocks need a restart or a human          |

**Resource allocation graph.** Draw processes as circles and resources as boxes; an edge from a resource to a process means it is _held_, an edge from a process to a resource means it is _requested_. With one instance of each resource, **a cycle means deadlock**. With several instances, a cycle is necessary but not sufficient.

**Safe state and the banker's algorithm.** A state is _safe_ if some order exists in which every process can get its remaining need and finish. For each process, `need = max - allocation`. Repeatedly find a process whose `need` fits in `work` (start with `available`), pretend it finishes and releases its allocation, and continue. If all finish, the order is a **safe sequence**.

```python
def safe_sequence(available, allocation, maximum):
    need = [[m - a for m, a in zip(mr, ar)] for mr, ar in zip(maximum, allocation)]
    work, done, order = list(available), [False] * len(allocation), []
    while len(order) < len(allocation):
        for i, row in enumerate(need):
            if not done[i] and all(n <= w for n, w in zip(row, work)):
                work = [w + a for w, a in zip(work, allocation[i])]
                done[i] = True
                order.append(i)
                break
        else:
            return None            # nobody can finish: unsafe
    return order

# The textbook example: 5 processes, resources A, B, C
print(safe_sequence([3, 3, 2],
                    [[0, 1, 0], [2, 0, 0], [3, 0, 2], [2, 1, 1], [0, 0, 2]],
                    [[7, 5, 3], [3, 2, 2], [9, 0, 2], [2, 2, 2], [4, 3, 3]]))
```

This state is safe. The code prints P1, P3, P0, P2, P4, and P1, P3, P4, P0, P2 is another valid order, so a state can have several safe sequences. To **avoid** deadlock, the banker pretends to grant each new request and runs this check; if the result is unsafe, the process waits.

**Detection** uses the same idea without the maximum claims: build a **wait-for graph** (process to the process it waits on) and look for a cycle. **Recovery** means killing one or all deadlocked processes (cheapest or youngest first), or preempting resources and rolling a process back to a checkpoint, taking care that the same victim is not picked every time.

# Cancellation

Python threads cannot be killed from outside, so a thread needs a way to be asked to stop:

```python
stop = threading.Event()
while not stop.is_set():
    try:
        job = jobs.get(timeout=0.1)       # wake up regularly to check the flag
    except queue.Empty:
        continue
    ...
```

In asyncio, `task.cancel()` raises `CancelledError` at the task's current `await`, and `async with asyncio.timeout(5):` cancels the block after five seconds. `asyncio.TaskGroup` cancels the siblings when one task fails. Every thread or task you start needs a way to stop.

# Worker pool

```python
import queue, threading
from collections.abc import Callable

def pool(n: int, jobs: "queue.Queue[object]", handle: Callable[[object], None], stop: threading.Event) -> None:
    DONE = object()                       # sentinel; the sender puts one per worker

    def worker() -> None:
        while not stop.is_set():
            try:
                j = jobs.get(timeout=0.1)
            except queue.Empty:
                continue
            if j is DONE:                 # closed: drain finished
                return
            try:
                handle(j)
            finally:
                jobs.task_done()

    threads = [threading.Thread(target=worker) for _ in range(n)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
```

The sender puts a sentinel for each worker when done (`jobs.put(DONE)` n times) or sets `stop` to cancel. Test: all jobs processed exactly once, cancel stops promptly, no leaked threads (`threading.enumerate()`). Then write the same pool with `concurrent.futures.ThreadPoolExecutor` and compare the code.

# Why `while`, not `if`

`while not items: cond.wait()`. Change `while` to `if` and run several consumers: one wakes after another consumed the item, then reads empty state (bug).

# Binary search variants

**Single element in a sorted array of pairs:** before the single element, pairs start at even indices; after it, at odd. Binary search on parity (always check with `mid` even: `mid ^ 1`).

```python
lo, hi = 0, len(a) - 1
while lo < hi:
    mid = lo + (hi - lo) // 2
    if a[mid] == a[mid ^ 1]:
        lo = mid + 1
    else:
        hi = mid
return a[lo]
```

**Count occurrences:** `upper_bound(x) - lower_bound(x)`.

**Square root (integer floor):** search the answer in `[0, x]` for the largest `m` with `m*m <= x` (compare as `m <= x // m` to avoid overflow in Java or C++; in Python `m * m` is safe, and `math.isqrt` is the built-in). **Nth root:** same with `pow(m, n)` compared to `x`, stopping early when it exceeds `x`.

**Smallest divisor with sum of ceilings ≤ threshold:** feasibility is monotonic in the divisor, so binary search `d` in `[1, max]`; `total += (v + d - 1) // d`.

# Pattern: binary search on the answer

If `feasible(x)` is monotonic (false...false true...true), find the first true.

```python
lo, hi = min_ans, max_ans
while lo < hi:
    mid = lo + (hi - lo) // 2
    if feasible(mid):
        hi = mid
    else:
        lo = mid + 1
```

Complexity: O(log(range) × cost of `feasible`).

1. **`while`, not `if`.** After `wait` returns, the condition isn't guaranteed: wake-ups may be spurious, and by the time you reacquire the lock another thread may have consumed the item or changed the state. Rechecking in a loop is the only safe pattern.
2. **Four conditions:** mutual exclusion, hold-and-wait, no preemption, circular wait. Lock ordering breaks **circular wait**.
3. **Safe state versus deadlock-free.** A state is **safe** if some order exists in which every process can obtain its maximum remaining need and finish. An **unsafe** state is not yet a deadlock; it only means deadlock is _possible_ depending on what processes request next. A deadlock-free state is one where no deadlock exists right now, and every deadlocked state is unsafe but not every unsafe state is deadlocked. The banker's algorithm is conservative: it refuses a request that would move the system from safe to unsafe, even though nothing is stuck yet, because it cannot rule out that processes will then ask for their declared maximums and deadlock. The price is that resources sit idle that a smarter, less cautious policy might have used.
4. **Which problem needs more than a mutex.** The **bounded buffer** needs _counting_: producers must wait when the buffer is full and consumers when it is empty, which a mutex alone cannot express; use semaphores (`empty`, `full`) or condition variables. **Readers-writers** needs more too: many readers may hold access at once but a writer needs exclusivity, with a policy to avoid starving writers. **Dining philosophers** is about avoiding deadlock (and starvation) when each thread needs two locks, solved by lock ordering or limiting the number at the table. All three need more than one plain mutex, but the bounded buffer is the clearest case, since its need is for waiting on a condition, not just excluding others.
