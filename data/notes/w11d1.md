# Complexity is the enemy (Ousterhout)

Complexity = anything that makes a system hard to understand or modify. Symptoms: **change amplification** (one change touches many places), **cognitive load** (much to know), **unknown unknowns** (can't tell what a change affects). Causes: **dependencies** and **obscurity**.

# Deep vs shallow modules

A module's cost is its **interface**; its benefit is the **functionality** behind it.

| Deep                                                                   | Shallow                                                 |
| ---------------------------------------------------------------------- | ------------------------------------------------------- |
| small interface, lots of hidden work                                   | interface about as complex as the implementation        |
| Unix file I/O: `open/read/write/close` hide caches, disks, permissions | a wrapper that forwards calls, or a class per tiny step |

```python
from typing import Protocol

# shallow: leaks every internal step
class Store(Protocol):
    def open(self) -> None: ...
    def lock(self) -> None: ...
    def seek(self, n: int) -> None: ...
    def write(self, b: bytes) -> None: ...
    def sync(self) -> None: ...
    def unlock(self) -> None: ...
    def close(self) -> None: ...

# deep: hides the log, index, fsync, compaction
class KV(Protocol):
    def get(self, k: str) -> bytes | None: ...
    def put(self, k: str, v: bytes) -> None: ...
    def delete(self, k: str) -> None: ...
```

Principles: **information hiding** (keep design decisions inside one module; leakage = the same knowledge in two places); **pull complexity downward** (make the module absorb it so callers don't); **define errors out of existence** (e.g. deleting a missing key succeeds); somewhat general-purpose interfaces; **strategic** (invest ~10-20% in design) over **tactical** programming; comments describe what isn't obvious from code.

# SOLID as questions to ask

| Letter | Principle             | Ask yourself                                                             |
| ------ | --------------------- | ------------------------------------------------------------------------ |
| S      | Single responsibility | does this class have one reason to change?                               |
| O      | Open/closed           | can I add a new case by adding code instead of editing working code?     |
| L      | Liskov substitution   | can a subclass stand in for its parent without surprising callers?       |
| I      | Interface segregation | am I forcing callers to depend on methods they never use?                |
| D      | Dependency inversion  | does the high-level logic depend on an abstraction I can swap in a test? |

```python
from typing import Protocol

class Store(Protocol):                       # the abstraction the service depends on
    def get(self, key: str) -> bytes | None: ...
    def put(self, key: str, value: bytes) -> None: ...

class Service:
    def __init__(self, store: Store) -> None:   # inject it: a real store or a fake in tests
        self.store = store
```

Treat them as prompts for a code review, not laws; over-applying them produces a maze of tiny classes, which Ousterhout calls shallow modules.

# Refactoring

Change structure **without changing behavior**, in small steps with **tests green** after each. Common moves: Rename, Extract Function, Inline, Move Function/Field, Introduce Parameter Object, Replace Conditional with Polymorphism, Split Phase. Refactor _before_ adding a feature that doesn't fit ("make the change easy, then make the easy change"). Don't mix refactor and behavior changes in one commit.

# Python module and package design

Small public surface: list it in `__all__` and in the package's `__init__.py`, and prefix everything else with an underscore. Keep implementation modules inside the package (`_log.py`, `_index.py`) and import only the public names from outside. **Accept protocols (or plain callables), return concrete types**; define a `Protocol` where it is _used_, not where it is implemented. Avoid `utils.py` and `common.py` dumping grounds, and avoid import cycles (they show up as `ImportError` at startup; fix them by moving shared types to a lower module).

# Patterns as vocabulary

Strategy, Adapter, Decorator, Observer, Factory... give names to recurring shapes so you can discuss them; don't force them.

# A few patterns in Python

- **Strategy:** pass behaviour in as a function or object instead of branching: `sorted(xs, key=len)`.
- **Adapter:** wrap an object so it matches the interface callers expect, such as a class that gives a file-like `read()` over a socket.
- **Decorator:** wrap a function to add behaviour without editing it: `@functools.cache`, `@retry(3)`.
- **Observer:** let others subscribe to events (callbacks or a list of handlers) so the source need not know them.
- **Factory:** a function that chooses which concrete class to build, keeping `if kind == ...` in one place.

# Audit checklist

For each package ask:

1. Can I describe what each module or package does in one sentence? Is its interface smaller than its implementation?
2. Does a caller need to know ordering rules ("call `lock` before `seek`")? That's leakage.
3. Are types/errors from internals exposed (e.g. file offsets, SQL rows)?
4. Is the same knowledge (record format, key encoding) in two places?
5. Do modules import each other in circles or via "god" classes?

# BST problems

**Validate a BST:** pass **bounds** down (a node must be within `(lo, hi)` set by _all_ ancestors), not just compare with immediate children.

```python
def valid(n: TreeNode | None, lo: float = float("-inf"), hi: float = float("inf")) -> bool:
    if n is None:
        return True
    if not (lo < n.val < hi):
        return False
    return valid(n.left, lo, n.val) and valid(n.right, n.val, hi)
```

(Or check that inorder is strictly increasing.)

**LCA in a BST:** walk down; if both targets are smaller go left, if both larger go right, else the current node is the LCA. O(h).

**Construct BST from preorder** in O(n): recurse with an **upper bound**; consume the next preorder value while it's `< bound`.

```python
def build(pre: list[int], bound: float = float("inf"), i: list[int] | None = None) -> TreeNode | None:
    i = i if i is not None else [0]                 # a one-element list is a mutable cursor shared by the recursion
    if i[0] == len(pre) or pre[i[0]] > bound:
        return None
    n = TreeNode(pre[i[0]])
    i[0] += 1
    n.left = build(pre, n.val, i)
    n.right = build(pre, bound, i)
    return n
```

**Inorder successor** (smallest value `> x`): walk down; if `x < node` record node as candidate and go left, else go right. Predecessor is symmetric.

```python
succ, n = None, root
while n:
    if x < n.val:
        succ, n = n, n.left
    else:
        n = n.right
```

All O(h).

# Naming

Names are the cheapest documentation. They should reveal **intent** and be **consistent**.

- Name by **what it is/does**, not how: `pending_writes`, not `list2`. Booleans read as predicates: `is_empty`, `has_leader`.
- **Scope decides length:** `i` in a 3-line loop; `replication_lag` for a module-level value.
- Don't repeat context: `kv.Store`, not `kv.KVStore`; `http.Server` not `http.HTTPServer` (**no stutter**).
- Python (PEP 8): `snake_case` for functions, variables and modules, `CapWords` for classes, `UPPER_CASE` for constants, a leading underscore for private names; avoid `get_` prefixes on simple attributes (use a property); avoid abbreviations except common ones (`ctx`, `err`, `buf`).
- If a name is hard to choose, the abstraction may be wrong.
- Rename freely with tools (your editor's rename, or `rope`/`ruff` fixes) and keep terms consistent across code, docs and UI.
