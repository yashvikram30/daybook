# Tokenization

Models operate on **integer token ids**, not characters or words. A tokenizer maps text ↔ ids.

**Byte-level BPE (byte-pair encoding):**

1. Start with the 256 byte values as base tokens (any string is representable; no "unknown").
2. Count adjacent token pairs over the training text; **merge the most frequent pair** into a new token (id 256, 257, …). Repeat until the vocabulary reaches the target size.
3. **Encode:** convert to bytes, then apply the learned merges in the order learned. **Decode:** ids → bytes → concatenate → UTF-8 decode (`errors="replace"`).

```python
def get_stats(ids):  # count adjacent pairs
    c = {}
    for p in zip(ids, ids[1:]): c[p] = c.get(p, 0) + 1
    return c
def merge(ids, pair, new):
    out, i = [], 0
    while i < len(ids):
        if i < len(ids)-1 and (ids[i], ids[i+1]) == pair: out.append(new); i += 2
        else: out.append(ids[i]); i += 1
    return out
# train: for k in range(num_merges): pair = max(stats, key=stats.get); ids = merge(ids, pair, 256+k)
```

Variants: WordPiece (BERT), SentencePiece/Unigram. Real tokenizers also **pre-split** text with a regex (so merges don't cross word/number boundaries) and add special tokens (`<|endoftext|>`).

# Why tokenizers cause odd behavior

- A token is often a chunk like `" the"` (with leading space), not a letter: the model never sees the letters of a word, so **counting letters, spelling, reversing strings** is hard.
- **Numbers** are split into irregular chunks, which hurts long **arithmetic**.
- Non-English text and code can take **more tokens** (higher cost, less context).
- Whitespace/case matter: `"hello"`, `" hello"`, `"Hello"` are different tokens.

# Vocabulary size trade-off

Bigger vocab → **shorter sequences** (cheaper attention, more text per context) but larger embedding/output matrices (`V × d`), rarer tokens that are under-trained, and costlier softmax. Smaller vocab → longer sequences, finer granularity. (GPT-2: 50,257; modern models ~100k-250k.)

# A tiny GPT (decoder-only transformer)

```
token ids → token embedding + position embedding → N × [LN → causal attention → +;  LN → MLP → +] → LN → Linear(d, V) → logits
loss = cross-entropy(logits[t], token[t+1])           # predict the next token
```

- Training data: random windows of `block_size` characters; targets are the inputs shifted by one. Initial loss ≈ `ln(vocab)` (≈ 4.17 for 65 chars).
- Generation: sample from `softmax(logits / T)`, append, repeat.
- **Temperature T:** `T<1` sharpens the distribution (more deterministic), `T>1` flattens it (more random), `T→0` = greedy argmax. It **doesn't change the model's knowledge or the ranking of tokens**, only how much probability the top ones get. (top-k/top-p are separate truncation rules.)

# Tokenizer

1. Train: `ids = list(text.encode("utf-8"))`; do `vocab_size - 256` merges; store `merges: dict[(int,int)] -> int`.
2. `encode(s)`: bytes → repeatedly merge the pair with the **lowest merge index** present until none applies.
3. `decode(ids)`: `b"".join(vocab[i] for i in ids).decode("utf-8", errors="replace")`, where `vocab[i] = vocab[a] + vocab[b]` for merged tokens.
4. **Round-trip tests:** `""`, `"hello"`, emoji `"👩‍💻"` (multi-codepoint), mixed scripts `"नमस्ते 世界"`, leading/trailing spaces, newlines. `assert decode(encode(s)) == s`.
5. Compare with a production tokenizer (`tiktoken.get_encoding("cl100k_base")`) on ten strings: spaces, numbers (`"12345678"`), code, non-English text; explain one difference (e.g. digits chunked differently, or your small vocab produces many more tokens).

# 2D (grid) DP

State is `dp[i][j]`; recurrence usually looks at the cell above and to the left.

| Problem                                          | Recurrence                                                                 |
| ------------------------------------------------ | -------------------------------------------------------------------------- |
| **Unique paths** (right/down)                    | `dp[i][j] = dp[i-1][j] + dp[i][j-1]` (= C(m+n−2, m−1))                     |
| **Unique paths II** (obstacles)                  | same, but `dp = 0` on an obstacle                                          |
| **Min falling path sum**                         | `dp[i][j] = a[i][j] + min(dp[i-1][j-1], dp[i-1][j], dp[i-1][j+1])`         |
| **Triangle** (min top→bottom)                    | bottom-up: `dp[j] = tri[i][j] + min(dp[j], dp[j+1])`                       |
| **Ninja's training** (no same activity two days) | `dp[day][last] = points[day][act] + max over act ≠ last of dp[day-1][act]` |

```python
def unique_paths(m: int, n: int) -> int:
    dp = [1] * n
    for _ in range(1, m):
        for j in range(1, n):
            dp[j] += dp[j - 1]            # 1D rolling row
    return dp[n - 1]

def min_triangle(t: list[list[int]]) -> int:          # bottom-up in O(n) space
    dp = t[-1].copy()
    for i in range(len(t) - 2, -1, -1):
        for j in range(len(t[i])):
            dp[j] = t[i][j] + min(dp[j], dp[j + 1])
    return dp[0]
```

Time O(mn), space O(n) with a rolling row.

# Property-based tests for encoders

An encoder/decoder has **laws** that hold for _every_ input; let a library hunt for counterexamples.

```python
from hypothesis import given, strategies as st

@given(st.text())
def test_roundtrip(s):
    assert tok.decode(tok.encode(s)) == s

@given(st.lists(st.integers(0, 255)))
def test_decode_never_crashes(ids):
    tok.decode(ids)                       # any id sequence → some string, no exception
```

Typical properties: **round trip**, **no crash on any input**, idempotent normalization (`norm(norm(x)) == norm(x)`), length bounds (`len(encode(s)) <= len(s.encode())`), concatenation (`decode(a+b) == decode(a)+decode(b)` where it should). Hypothesis **shrinks** a failure to a minimal example (e.g. a lone surrogate or emoji sequence).
