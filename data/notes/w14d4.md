# Streaming with Server-Sent Events (SSE)

One long-lived HTTP response, `Content-Type: text/event-stream`; the server writes events and flushes:

```
event: content_block_delta
data: {"type":"content_block_delta","delta":{"type":"text_delta","text":"Hel"}}

data: next event...        ← events end with a blank line
```

Why stream: **time to first token** (perceived latency) drops from the full generation time to a fraction of a second. Claude's stream emits `message_start`, `content_block_start`, many `content_block_delta`, `content_block_stop`, `message_delta` (stop reason, usage), `message_stop` (plus `ping`). Browsers consume it with `EventSource` (GET only, auto-reconnect) or `fetch` streams.

```python
import httpx
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse

app = FastAPI()
TIMEOUT = httpx.Timeout(30.0, connect=3.0)           # connect 3 s; each read waits at most 30 s

async def relay(request: Request, payload: dict):
    async with httpx.AsyncClient(timeout=TIMEOUT) as client:
        async with client.stream("POST", UPSTREAM_URL, json=payload) as upstream:
            async for line in upstream.aiter_lines():
                if await request.is_disconnected():
                    break                              # leaving the `async with` blocks closes the upstream stream
                if line:
                    yield line + "\n"                  # SSE lines pass through; blank lines separate events
                else:
                    yield "\n"

@app.post("/v1/chat")
async def chat(request: Request):
    payload = await request.json()
    return StreamingResponse(
        relay(request, payload),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache"},
    )
```

# Tracing a request

A **trace** follows one request through many components; a **span** is one timed step inside it (the HTTP handler, the retrieval call, the model call), with a parent span and attributes. **OpenTelemetry** is the standard way to emit them. Its generative-AI conventions name the useful attributes for a model span: model name, input and output token counts, finish reason, and latency. With them you can answer "why was this request slow or expensive?" by reading one trace: for example, a long prompt (many input tokens) or a retry that doubled the time. Log a request id on every line so logs and traces join up.

# Cancellation

When the client disconnects, the server cancels the task that is writing the response, and that cancellation (`asyncio.CancelledError`) travels up through your generator. **Keep the upstream call inside `async with` blocks**, so the cancellation closes the upstream stream and you **stop paying for tokens** nobody will read; also check `request.is_disconnected()` between events. Bound the whole call with a timeout as well (`async with asyncio.timeout(60):`). Never catch `CancelledError` and carry on.

# Retries, limits

- Retry **before any bytes are streamed** on `429` (honor `Retry-After`), `5xx`/overloaded; **don't retry other 4xx**. After streaming began, a retry would duplicate or restart output: surface an error or resume explicitly.
- **Exponential backoff + full jitter + a retry budget** (e.g. retries ≤ 10% of requests). Without jitter and a budget, every client retries in lockstep and **multiplies load on a provider that is already struggling** (retry storm).
- **Per-key rate limiting** with a token bucket (limit requests and tokens/min); return `429` + `Retry-After`; attach a **request id** to every log line and upstream call.

# Metrics (and which question each answers)

| Metric                                                                    | Answers                         |
| ------------------------------------------------------------------------- | ------------------------------- |
| **time to first token** (p50/p95), total duration histogram               | are users **waiting too long**? |
| input/output **tokens per request**, cache hit ratio, cost counters       | is **cost drifting**?           |
| error counts by status/type, retries, rate-limit rejects, in-flight gauge | reliability / saturation        |

OpenTelemetry GenAI conventions standardize attribute names (e.g. `gen_ai.request.model`, `gen_ai.usage.input_tokens`). **Logs** say _what happened_, **metrics** say _how bad/when_, **traces** say _where the time went_.

# Gateway pieces

1. **Fake upstream** (test server) emitting SSE tokens every 20 ms, with knobs from your faultnet: fail N times with `529/500`, stall before the first token, close mid-stream, return `429` + `Retry-After`.
2. **Gateway handler:** auth (API key → client id, as a FastAPI dependency) → rate limit (one token bucket per key) → open the upstream stream with `httpx` inside `async with` → yield events to the client as they arrive; record TTFT at the first token.
3. **Retry wrapper** (only before the first byte): attempts ≤ 3, `sleep = rand(0, min(cap, base·2^n))`, honor `Retry-After`, shared **retry budget**.
4. **Timeouts:** connect, first-byte, overall; return `504` if exceeded.
5. **Metrics** (`prometheus_client`): `llm_ttft_seconds`, `llm_request_seconds`, `llm_tokens_total{dir="in|out"}`, `llm_errors_total{kind}`, `llm_inflight`.
6. **Tests** (pytest with `httpx.ASGITransport` and a fake upstream app): client cancels mid-stream → the fake upstream sees the cancellation (its generator's `finally` runs) within ms; stalled upstream → 504; 2× `529` then success → client sees one stream and the retry counter increments; limiter returns `429` beyond the burst.

# LCS and subsequence DP

**Longest common subsequence:** `dp[i][j]` = LCS of `s[:i]`, `t[:j]`.

```python
dp = [[0] * (len(t) + 1) for _ in range(len(s) + 1)]
for i in range(1, len(s) + 1):
    for j in range(1, len(t) + 1):
        if s[i - 1] == t[j - 1]:
            dp[i][j] = dp[i - 1][j - 1] + 1
        else:
            dp[i][j] = max(dp[i - 1][j], dp[i][j - 1])
```

O(mn) time; O(min(m,n)) space with a rolling row. Reconstruct by walking back from `dp[m][n]`.

**LIS variants** (all O(n²) DP over pairs `j < i`):

| Problem                         | DP                                                                                                          |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **Longest string chain**        | sort words by length; `dp[w] = 1 + max(dp[pred])` for each predecessor made by deleting one char (hash map) |
| **Longest bitonic subsequence** | `inc[i]` (LIS ending at i) + `dec[i]` (LDS starting at i, from the right) − 1; take the max                 |
| **Number of LIS**               | keep `len[i]` and `cnt[i]`: if `len[j]+1 > len[i]` reset `cnt[i]=cnt[j]`; if equal add `cnt[j]`             |

Relationship: `LCS(a, b)` with `b` = sorted-unique(`a`) gives LIS.

# Observability: logs, metrics, traces

Three signals, three questions:

| Signal                                            | Cost           | Best for                                                             |
| ------------------------------------------------- | -------------- | -------------------------------------------------------------------- |
| **Metrics** (numbers over time, aggregated)       | low            | "is something wrong, how bad, since when?": dashboards, alerts, SLOs |
| **Traces** (one request across services as spans) | medium         | "**where** did the time go / which dependency failed?"               |
| **Logs** (events with context)                    | high at volume | "**why**, what exactly happened?"                                    |

Practice: propagate a **trace/request id** through every hop and into every log line; use **structured** logs; keep metric **label cardinality low** (never raw user ids/URLs); alert on **symptoms** (error rate, p95 TTFT) not causes; define **SLOs**. For an LLM gateway add: model name, token counts, cache hits, retries, stop reasons.

1. **Client disconnects.** The upstream request should be **cancelled** (stop generation, stop billing, free the connection). In an asyncio server the response task is cancelled on disconnect; keep the upstream call in `async with` blocks (and check `request.is_disconnected()` in the copy loop) so the upstream stream is closed.
2. **Jitter and budget.** Without jitter, clients that failed together retry together in synchronized waves; without a budget, retries multiply traffic (each request becomes 3+). A struggling provider gets hit harder and can't recover (retry storm).
3. **Metrics.** Users waiting too long → time-to-first-token and total-duration p95/p99. Cost drifting → tokens in/out per request (and cache hit ratio), cost counters, requests per client.
