# B+tree

A balanced, multiway search tree where **each node is a page**.

```
              [ 30 | 60 ]                    internal: keys + child pointers only
             /     |     \
   [10 20] → [30 40 50] → [60 70 80]         leaves: all keys (+ values), linked left→right
```

- **High fanout:** a 4 KB page holds ~200-300 (key, pointer) pairs, so each level multiplies reach by hundreds. Height = `⌈log_f N⌉`: with f=200, **1M keys → 3 levels**, 1B keys → 4 levels. Each lookup costs height page reads (top levels are cached).
- **Search:** binary search in each node. **Range scan:** find the start leaf, follow leaf links.
- **Insert:** find the leaf; if full, **split** in half and push the separator up (may cascade; root split grows height by 1).
- **Delete:** remove; if underfull, borrow from a sibling or **merge**.
- B-tree (classic) stores values in internal nodes too; B+tree keeps them only in leaves (more keys per internal node, better scans).

# LSM tree (log-structured merge)

```
write → WAL (append) + memtable (sorted, in RAM)
memtable full → flush as immutable sorted SSTable (L0)
background compaction merges SSTables (drops overwritten/deleted keys)
read → memtable → newest SSTable → ... → oldest (Bloom filters skip files)
```

# Comparison

|             | B+tree                                   | LSM tree                                    |
| ----------- | ---------------------------------------- | ------------------------------------------- |
| Writes      | in-place page updates (random I/O) + WAL | sequential appends, batched                 |
| Point reads | one path, predictable                    | may check several files (read amp)          |
| Range scans | excellent (linked leaves)                | merge across files                          |
| Space       | page fill ~50-70%                        | stale versions until compaction (space amp) |
| Write amp   | page rewrite per small write             | repeated compaction rewrites                |
| Examples    | Postgres, MySQL/InnoDB, SQLite           | RocksDB, LevelDB, Cassandra                 |

Pick **LSM** for write-heavy/ingest workloads (logs, time series, messaging); **B+tree** for read-heavy, low-latency point and range queries.

# Index basics

An index is an extra sorted structure over some columns. Composite index `(a, b)` helps queries on `a` or `a,b`, not `b` alone (**leftmost prefix**). A **covering** index holds every needed column, avoiding table lookups.

# In-memory B-tree (order t)

```python
from bisect import bisect_left
from dataclasses import dataclass, field

T = 16                                    # max keys = 2*T - 1

@dataclass
class Node:
    keys: list[int] = field(default_factory=list)
    vals: list[str] = field(default_factory=list)
    kids: list["Node"] = field(default_factory=list)      # leaf when empty

    def search(self, k: int) -> str | None:
        i = bisect_left(self.keys, k)
        if i < len(self.keys) and self.keys[i] == k:
            return self.vals[i]
        if not self.kids:
            return None
        return self.kids[i].search(k)
```

**Insert (proactive split):** walking down, split any full child before descending (median key moves up), then insert into the leaf. If the root is full, create a new root and split.

# Benchmark

1M random keys: insert and get for the B-tree vs a `dict` vs a sorted list kept with `bisect.insort` (binary search; insert O(n) shifting). Expect `dict` fastest for point lookups, since it is native code and your B-tree is Python; B-tree wins on ordered iteration/range and beats the sorted list for inserts. Python overhead dominates small differences, so look at how the curves grow with N rather than the absolute times.

# Implementations

**Array stack:** a Python `list`; `push` is `append`, `pop` is `pop()`; O(1).
**Array queue:** circular buffer with `head` and `size` (index `(head+size)%cap`); O(1) enqueue/dequeue.

**Queue using two stacks** (amortized O(1)): `in` receives pushes; `out` serves pops; when `out` is empty, move everything from `in` to `out` (reverses order).

```python
class MyQueue:
    def __init__(self) -> None:
        self.inbox: list[int] = []
        self.outbox: list[int] = []

    def push(self, x: int) -> None:
        self.inbox.append(x)

    def pop(self) -> int:
        if not self.outbox:
            while self.inbox:
                self.outbox.append(self.inbox.pop())
        return self.outbox.pop()
```

**Stack using queues:** one queue, push then rotate `len−1` elements to the back (push O(n), pop O(1)); or two queues.

**Linked-list stack:** push/pop at head. **Linked-list queue:** keep `head` and `tail`; enqueue at tail, dequeue at head.

| Structure      | push/enqueue   | pop/dequeue | Note                               |
| -------------- | -------------- | ----------- | ---------------------------------- |
| array stack    | O(1) amortized | O(1)        | dynamic array growth               |
| circular queue | O(1)           | O(1)        | fixed capacity                     |
| linked list    | O(1)           | O(1)        | pointer overhead, cache-unfriendly |

Python has no separate stack or queue types: use a `list` for a stack (`append`, `pop()`) and `collections.deque` for a queue (`append`, `popleft()`, both O(1); `list.pop(0)` is O(n)).

# Read the EXPLAIN output

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE customer_id = 42;
```

Read the plan **inside-out** (deepest nodes run first). Each node: `cost=startup..total`, estimated `rows`, and with ANALYZE the **actual** time and rows.

| Node                                 | Meaning                                                        |
| ------------------------------------ | -------------------------------------------------------------- |
| Seq Scan                             | read the whole table                                           |
| Index Scan / Index Only Scan         | use a B-tree (only: no heap visit)                             |
| Bitmap Heap Scan                     | many matches, fetch pages in order                             |
| Nested Loop / Hash Join / Merge Join | join strategies (small×indexed / big equality / sorted inputs) |
| Sort, Aggregate                      | may spill to disk when too large                               |

Red flags: `Seq Scan` with a selective filter on a big table (missing index); **estimated rows vs actual rows off by 10×+** (stale stats → `ANALYZE`); sorts spilling to disk; high "Rows Removed by Filter". `EXPLAIN` alone shows the plan; `ANALYZE` actually **runs** the query.
