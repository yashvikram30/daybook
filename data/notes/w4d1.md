# Data race

Two threads access the same memory, at least one writes, with no synchronization. `counter++` is **three steps** (load, add, store); a preemption between load and store lets two threads both read the same old value, so one update is lost. This happens even on one core, because the OS can switch threads between those instructions. In Python `n += 1` is `LOAD_GLOBAL`, `LOAD_CONST`, `BINARY_OP`, `STORE_GLOBAL` (`dis.dis` shows them), so a lost update needs the interpreter to hand the GIL to another thread somewhere between the load and the store.

Since Python 3.10 the interpreter only checks for such a hand-off at certain points (loop jumps and function calls), so on a normal GIL build a bare `n += 1` loop usually gives the right total. That is luck of the implementation, not a guarantee. Put a call between the read and the write and the race is easy to see:

```python
import sys, threading

sys.setswitchinterval(1e-6)       # switch threads far more often than the 5 ms default
n = 0

def add(a: int, b: int) -> int:
    return a + b                  # a call is a point where the GIL can change hands

def work() -> None:
    global n
    for _ in range(200_000):
        n = add(n, 1)             # read n, call, write n: the call is the gap

ts = [threading.Thread(target=work) for _ in range(4)]
for t in ts: t.start()
for t in ts: t.join()
print(n)                          # far below 800,000 (about half, on 3.12 to 3.14)
```

On a free-threaded build (3.13t, no GIL) even the bare `n += 1` loop loses most of its updates. A correct-looking run proves nothing, and the reverse is also true: a program that happens to give the right total on your build is still wrong.

# Four fixes

| Tool                                | How                                   | Rough cost (uncontended)                                                          | Use for                       |
| ----------------------------------- | ------------------------------------- | --------------------------------------------------------------------------------- | ----------------------------- |
| `threading.Lock`                    | `with lock: n += 1`                   | tens to hundreds of ns; contended: threads block and the GIL is handed around, µs | critical sections of any size |
| owner thread + `queue.Queue`        | one thread owns `n`, the others `put` | about a µs per operation                                                          | ownership/handoff             |
| per-thread counts, then sum         | no sharing                            | fastest                                                                           | when possible                 |
| processes + `multiprocessing.Value` | shared memory with its own lock       | slower per operation, but real parallelism                                        | CPU-bound work                |

There is no `atomic` integer in pure Python. Some operations happen to be safe under the GIL (a single `list.append`, `dict[key] = value`), but that is an implementation detail and `n += 1` is not one of them. Do not build on it.

Rule of thumb: share as little as you can, and where you must share, put a lock around the whole read-modify-write. A lock is fine (often better) for protecting state.

# The critical-section problem

The code that touches shared data is a **critical section**. A correct solution needs three properties:

1. **Mutual exclusion:** at most one thread is inside at a time.
2. **Progress:** if nobody is inside and some thread wants in, one of them gets in soon; threads outside the section cannot block the decision.
3. **Bounded waiting:** once a thread asks to enter, only a limited number of others can go in before it.

**Peterson's solution** (two threads, software only): each thread says it wants in and politely gives the other the turn.

```python
flag = [False, False]     # flag[i]: thread i wants to enter
turn = 0

def enter(i: int) -> None:
    global turn
    other = 1 - i
    flag[i] = True
    turn = other                         # "you go first"
    while flag[other] and turn == other:
        pass                             # spin

def leave(i: int) -> None:
    flag[i] = False
```

It satisfies all three properties on a machine that runs the steps in program order. On a modern CPU, stores and loads can be reordered, so it needs memory barriers; this is why real locks use hardware support instead.

**Hardware support:** an **atomic** instruction does a read and a write in one indivisible step. `test_and_set(lock)` returns the old value and sets it to true; a thread that gets `False` has the lock.

```
while test_and_set(lock): pass   # spin until the old value was False
...critical section...
lock = False
```

A spinning lock wastes CPU while it waits, so an OS lock puts the waiting thread to sleep instead (a **futex** on Linux). Python's `threading.Lock` does exactly that.

# Threads and their models

A **thread** is a flow of control inside a process. Threads of one process share the code, heap and open files, but each has its own stack and registers, which is why they are cheap to create and why they race. Mapping user threads onto kernel threads is done in one of three ways: **many-to-one** (all user threads on one kernel thread, so one blocking call blocks everything, as with asyncio's single thread), **one-to-one** (each user thread has a kernel thread, which is how Linux and `threading` work) and **many-to-many** (a pool of kernel threads runs many user threads, the idea behind Go's goroutines).

# Finding races in Python

There is no built-in race detector like the one some languages ship. Instead:

- **Stress it:** `sys.setswitchinterval(1e-6)`, many threads, many iterations, run the test hundreds of times.
- **Time-box it:** a deadlocked or stuck test should fail, not hang. Use `pytest-timeout`, and `faulthandler.dump_traceback_later(10)` to print every thread's stack when it hangs.
- **Check the invariant**, not just "it didn't crash": the final total, no lost items, no duplicates.
- A free-threaded build (3.13t) removes the GIL's accidental protection, so races that were hidden start to show.

# Rotated sorted arrays

A rotated sorted array has a **sorted half** at every split. At `mid`, one of `[lo,mid]` / `[mid,hi]` is sorted; test whether the target lies in the sorted half to decide where to go.

```python
def search(a: list[int], t: int) -> int:
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = lo + (hi - lo) // 2
        if a[mid] == t:
            return mid
        if a[lo] <= a[mid]:                      # left half sorted
            if a[lo] <= t < a[mid]:
                hi = mid - 1
            else:
                lo = mid + 1
        else:                                    # right half sorted
            if a[mid] < t <= a[hi]:
                lo = mid + 1
            else:
                hi = mid - 1
    return -1
```

**With duplicates:** if `a[lo]==a[mid]==a[hi]` you can't tell which half is sorted → `lo++, hi--`. Worst case O(n).

**Minimum / rotation count:** compare `a[mid]` with `a[hi]`: if `a[mid] > a[hi]` the min is right of mid, else it's at mid or left. The **index of the minimum = number of rotations**.

```python
lo, hi = 0, len(a) - 1
while lo < hi:
    mid = lo + (hi - lo) // 2
    if a[mid] > a[hi]:
        lo = mid + 1
    else:
        hi = mid
```

**First/last occurrence:** `lower_bound(x)` and `upper_bound(x)-1` (`bisect_left` and `bisect_right`).

# Testing concurrent code

- Repeat the test (`pytest --count=100` with pytest-repeat, or a loop) and run in random order (`pytest -p randomly` with pytest-randomly) to expose order dependence. Lower `sys.setswitchinterval` in the test to make interleavings more likely.
- **Don't `time.sleep` to "wait for" threads**: flaky. Use `thread.join()`, `queue.Queue.join()`, `threading.Event.wait(timeout)` or futures, and for asyncio `asyncio.timeout` or `asyncio.wait_for`.
- Test with the property you care about (final total, no deadlock, all results received), under a **timeout** (`pytest-timeout`, or `faulthandler.dump_traceback_later`).
- Detect leaked threads: `threading.enumerate()` at the end of the test should show only the main thread, and pytest's `-W error` turns unawaited-coroutine warnings into failures.
- Keep concurrency out of business logic so most code is testable sequentially.

1. **Lost updates on one core.** `counter++` compiles to load/add/store. The scheduler may preempt a thread after its load; another thread then loads the same value, both store `old+1`. Atomicity needs a lock or an atomic instruction. The GIL does not make a read-modify-write atomic: the interpreter can hand it to another thread between the read and the write (at a call or loop jump on current GIL builds, anywhere on a free-threaded build), so correct code locks the whole update.
2. **Mutex cost.** Uncontended: a single atomic compare-and-swap (~tens of ns). Contended: waiters block (a futex underneath), costing a context switch, GIL hand-offs and cache-line transfers (µs), and throughput collapses as threads queue.
3. **Thread vs task vs process.** A Python thread is a real OS thread, scheduled by the kernel, but only one runs Python bytecode at a time because of the GIL; it can run in parallel only while another is blocked in I/O or in native code that releases the GIL. An asyncio task is a coroutine in one thread, switched cheaply in user space only at `await`. A process has its own interpreter and GIL, so it gives real parallelism for CPU-bound work at the price of separate memory and slower communication.
4. **Critical section and Peterson.** The three requirements: **mutual exclusion** (at most one inside), **progress** (if nobody is inside and someone wants in, the choice of who enters cannot be postponed forever or depend on threads that are not trying), and **bounded waiting** (a limit on how many others can enter ahead of a waiting thread). Peterson's algorithm uses `flag[i]` and `turn`. _Mutual exclusion:_ thread `i` enters only if `flag[other]` is false or `turn == i`; if both were inside, each would have seen `turn` equal to itself, but `turn` holds one value, a contradiction. _Progress:_ a thread outside its critical section has `flag` false, so it never blocks the other; if both want in, `turn` decides. _Bounded waiting:_ after thread `i` sets `turn = other` and the other leaves and tries again, it sets `turn = i`, so `i` enters after at most one turn of the other thread.
