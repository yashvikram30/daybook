# C4: four zoom levels

1. **System context:** your system, its users and external systems.
2. **Containers:** separately deployable/runnable units (apps, databases, queues).
3. **Components:** major building blocks inside a container.
4. **Code:** classes/functions (rarely drawn).

Capstone containers diagram:

```
 client ──HTTPS──► gateway (async Python): auth · rate limit · request id · metrics
                      │            │ timeouts + circuit breaker
                      │            ▼
                      │        rag-service (Python/FastAPI): rewrite → retrieve → rerank → generate
                      │            │               │                 │
                      ▼            ▼               ▼                 ▼
              KV cache (Raft ×3)  vector store   LLM upstream     (traces/metrics)
```

# Docker Compose

One file runs the whole system locally:

```yaml
services:
  kv1: { build: ./kv, command: ["--id=1", "--peers=kv2:7000,kv3:7000"] }
  kv2: { build: ./kv, command: ["--id=2", "--peers=kv1:7000,kv3:7000"] }
  kv3: { build: ./kv, command: ["--id=3", "--peers=kv1:7000,kv2:7000"] }
  db: { image: pgvector/pgvector:pg16, environment: { POSTGRES_PASSWORD: pw } }
  rag: { build: ./rag, depends_on: [db], environment: { LLM_BASE_URL: "${LLM_BASE_URL}" } }
  gateway: { build: ./gateway, ports: ["8080:8080"], depends_on: [rag, kv1] }
```

`docker compose up --build`; use health checks (`depends_on: condition: service_healthy`); keys come from `.env` (gitignored).

# Circuit breaker (recap)

**Closed** (normal) → **open** after N consecutive failures (fail fast) → **half-open** after a cooldown (trial request; success closes, failure re-opens). Put one between the gateway and the RAG service.

# ADRs

One short record per major decision (context, decision, consequences, alternatives): Raft KV as cache, hybrid retrieval, tenant isolation approach, timeouts/breaker policy.

# Definition of done (production readiness)

Works and is **tested** (unit, integration, eval gate) · **documented** (README, architecture, runbook) · **observable** (logs, metrics, traces, dashboards, alerts) · **secure** (authn/z, secrets, rate limits, tenant tests) · **deployable** and **rollback-able** · failure modes known and tested · SLOs defined.

# Wiring checklist

1. **Gateway:** `X-API-Key` → tenant; per-key token bucket; generate `X-Request-Id`; forward to the RAG service with timeout + breaker; check the Raft KV cache first (miss on error); Prometheus metrics; structured logs.
2. **RAG service:** `/v1/ask` as in the previous days; `LLM_BASE_URL` points to the real provider or a **fake LLM** (for tests/CI).
3. **Compose:** all services start with `docker compose up --build`; health checks; a seed script that ingests the docs set.
4. **CI (GitHub Actions):** lint (`ruff`, `mypy`), unit tests with the fake LLM (`pytest`), build the three images, then the **eval gate**: start compose, run the golden set, **fail** if `hit@5 < 0.8` or faithfulness/abstention drop below thresholds (compare with a stored baseline).

```yaml
- run: docker compose up -d --wait
- run: python eval/run.py --golden eval/golden.json --min-hit5 0.8 --min-faithful 0.85
```

5. **README:** prerequisites, `cp .env.example .env`, `docker compose up`, a `curl` that returns a cited answer, how to run tests/evals, architecture link, troubleshooting. Test it from a clean clone, aiming at five minutes.

# Union-find applications

Whenever the question is "are these connected / how many groups / merge groups", think DSU.

| Problem                                                            | Idea                                                                                                                      |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| **Operations to make a network connected** (`n` computers, cables) | need `≥ n−1` cables else `-1`; answer = `components − 1` (move spare cables)                                              |
| **Accounts merge**                                                 | union all emails of an account (and across accounts sharing an email); group emails by root; sort                         |
| **Number of islands II** (cells turn to land one by one)           | on each addition, union with land neighbors; `count++`, then `count--` per successful union; report count after each step |
| **Making a large island** (flip one 0)                             | DSU of existing islands with sizes; for each `0`, sum sizes of **distinct** neighboring roots + 1                         |

```python
def make_connected(n: int, conns: list[list[int]]) -> int:
    if len(conns) < n - 1:
        return -1
    d = DSU(n)
    comps = n
    for a, b in conns:
        if d.union(a, b):
            comps -= 1
    return comps - 1

# making a large island: collect distinct roots around a 0 so a size isn't counted twice
seen: set[int] = set()
size = 1
for nr, nc in neighbours(r, c):
    root = d.find(nr * cols + nc)
    if root not in seen:
        seen.add(root)
        size += d.sz[root]
```

DSU also gives **cycle detection** in an undirected graph (`union` returns false) and powers Kruskal's MST.

# Definition of done for a service

Code that "works on my machine" isn't done. A checklist you can say yes to:

| Area          | Done means                                                                                         |
| ------------- | -------------------------------------------------------------------------------------------------- |
| Correctness   | tests (unit, integration), eval gate, edge and failure cases tested                                |
| Reliability   | timeouts, retries with backoff + jitter, circuit breakers, graceful degradation, load tested, SLOs |
| Security      | authn/authz, tenant isolation tested, secrets managed, input validated, dependencies scanned       |
| Observability | structured logs, metrics (golden signals), traces, dashboards, **actionable alerts**               |
| Operations    | one-command run, CI/CD, rollback, runbook, on-call knows how to debug                              |
| Docs          | README (5-minute start), architecture, ADRs, API spec                                              |
| Cost/capacity | estimates, limits, budgets                                                                         |

Write it down, review against it, and treat unchecked boxes as known risks with owners.

1. **Single point of failure vs slowdown.** Typically the gateway (and the RAG service) take the whole system down; failure of the KV cache only increases latency/cost (cache misses), and the vector store falling back to keyword search degrades quality, not availability. Your own diagram decides: list each component and its failure effect.
2. **CI protects against** regressions in code, builds and measured retrieval/answer quality. **Still reaches users:** problems that only appear with real data and traffic, provider outages/behavior changes, new prompt-injection patterns, gaps in the golden set, config/infra differences.
3. **Regret under 2× requirements.** _Personal answer:_ name the decision, the constraint it hits (e.g. single Raft group, in-memory index, one vector store), and what you'd change (shard, partition, async ingestion).
