# Why replicate

**Availability** (survive node loss), **latency** (data near users), **read throughput**.

# Leader-follower replication

```
client ──write──► LEADER ──replication log──► follower 1
                     │                    └► follower 2
client ──read ───► leader (fresh)  or  follower (maybe stale)
```

| Mode          | Leader acks when       | Cost                                                                           |
| ------------- | ---------------------- | ------------------------------------------------------------------------------ |
| **Async**     | it has written locally | fast and available; **a failover can lose acknowledged writes**; followers lag |
| **Sync**      | followers confirmed    | no loss; **blocks if a follower is down/slow → lower availability**            |
| **Semi-sync** | one follower confirmed | common compromise                                                              |

Problems from lag: **stale reads**, violating _read-your-writes_ (you write, then read an old value from a follower) and _monotonic reads_ (time goes backwards across replicas). Failover problems: lost writes, **split brain** (two leaders), picking a follower that's behind.

Other topologies: **multi-leader** (needs conflict resolution), **leaderless** (Dynamo/Cassandra: write to W of N, read from R, with **W + R > N** for overlapping quorums, plus read repair).

# Consistency models (strong → weak)

| Model            | Guarantee                                                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Linearizable** | behaves like a single copy; each operation takes effect atomically at some instant between its invocation and response; real-time order respected |
| Sequential       | all see the same order, consistent with each process's order (not real time)                                                                      |
| Causal           | causally related operations seen in order; concurrent ones may differ                                                                             |
| **Eventual**     | if updates stop, replicas converge; **no guarantee in the meantime**                                                                              |

**Linearizability promises** that once a read returns a new value, every later read anywhere returns it (or newer); eventual consistency promises only eventual convergence.

# Quorums and state machine replication

**Quorums.** With `N` replicas, a write must reach `W` of them and a read must ask `R`. If `W + R > N`, every read set overlaps every write set in at least one replica, so a read sees the latest acknowledged write (given versions to tell which is newest). With `N = 3`, `W = 2`, `R = 2` it tolerates one failed node on either path; `W = N`, `R = 1` makes reads fast and writes fragile; `W = 1`, `R = N` is the reverse. A quorum is also a _majority_ idea: any two majorities share a node, which is why consensus needs `2f + 1` nodes to survive `f` failures.

**State machine replication.** Make a service deterministic (the same inputs in the same order always produce the same state), give every replica the same ordered **log** of commands, and each replica ends in the same state. The hard part is getting everyone to agree on the log order, which is what consensus (Raft, next) provides. The same idea, a log feeding a deterministic machine, is how databases replicate (the WAL shipped to followers) and how your key-value store will become fault tolerant.

**Linearizability** is the strictest single-object guarantee. Every operation appears to take effect at one instant between its start and its end, and that order respects real time. If client A finishes a write before client B starts a read, B must see it. It costs coordination, which is why many systems offer weaker models.

# CAP, carefully

During a **network partition** a system must choose: stay **consistent** (linearizable; refuse some requests) or stay **available** (answer from possibly stale data). Kleppmann's critique: CAP's definitions are narrow and binary, systems aren't simply "CP or AP"; describe **precise guarantees** instead (and note latency trade-offs, PACELC).

# Tree views and orders

**Symmetric tree:** `mirror(a, b)`: both `None` → true; one `None` → false; `a.val == b.val and mirror(a.left, b.right) and mirror(a.right, b.left)`.

**Children sum property** (make `node = left + right` by only increasing values): push the deficit **down** on the way in (`if sum < node.val`, raise children to `node.val`), then fix up on the way out (`node.val = left + right`).

**Zig-zag level order:** BFS, reverse every other level (or fill the level slice from the right).

```python
for _ in range(len(q)):
    ...                                   # pop a node, take its value v
    level.append(v) if ltr else level.insert(0, v)       # or use a deque and appendleft
ltr = not ltr
```

**Boundary traversal:** root, **left boundary** (excluding leaves), all **leaves** left→right, **right boundary** (excluding leaves) in **reverse**.

**Vertical order:** DFS/BFS assigning `(col, row)`; group by `col` ascending, within a column sort by `row`, then by value.

```python
items: list[tuple[int, int, int]] = []        # (col, row, val): collect, then items.sort()
```

Top-to-bottom, left-to-right inside each column.

Complexity: O(n) (O(n log n) with the vertical-order sort).

# Write down the guarantees

An API without stated guarantees gets used with the **strongest assumptions** its users can imagine. Document, for each operation:

- **Consistency:** "reads from the leader are linearizable; follower reads may lag by up to X."
- **Durability:** "acknowledged writes survive a leader crash only if replicated to ≥ 1 follower."
- **Ordering, idempotency, error semantics** (what does a timeout mean? did the write happen?).

Record the decision in an **Architecture Decision Record (ADR)**:

```
Title: Reads may be served by followers
Status: accepted
Context: leader is the read bottleneck; most reads tolerate staleness
Decision: followers serve reads; clients needing fresh data pass ?consistency=strong
Consequences: stale reads up to replication lag; read-your-writes only via the leader
```

1. **Linearizability vs eventual.** Linearizable systems act like one copy: after a write completes, every subsequent read (from anywhere) sees it, and operations respect real-time order. Eventual consistency only promises convergence once writes stop, so reads can be stale or out of order meanwhile.
2. **Sync replication.** The leader must wait for follower acknowledgements, so if a follower is slow, partitioned or down, writes stall or fail: availability falls with every required replica. Semi-sync (wait for one) limits this.
3. **Why W + R > N works.** There are `N` replicas; a write is stored on at least `W` of them and a read asks at least `R`. Since `W + R > N`, the set that acknowledged the write and the set that answers the read must **share at least one replica** (by counting, they cannot fit in `N` without overlapping). That replica holds the latest write, and with version numbers or timestamps the reader picks the newest value among the replies. It guarantees freshness only if a write really reached `W` replicas, and it does not give full linearizability by itself (concurrent writes, sloppy quorums and failures can still expose stale or conflicting values).
