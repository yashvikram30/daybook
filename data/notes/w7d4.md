# LSM components

```
Put ──► WAL (append, fsync)  +  memtable (sorted, RAM)
                                  │ full (e.g. 4 MB)
                                  ▼
                       SSTable (immutable, sorted file)
                       [data blocks][index][bloom filter][footer]
Get ──► memtable → SSTable (newest) → ... → SSTable (oldest)   first hit wins
```

- **Memtable:** sorted in memory (skip list / balanced tree). The **WAL** makes it durable; replay it on restart.
- **SSTable:** immutable sorted key/value file with a sparse **index** (binary search to the block) and a **Bloom filter**.
- **Read order matters:** newer data shadows older. Reading old tables first can return a **stale** value (or resurrect a deleted key; a **tombstone** in a newer table must hide older values).
- **Compaction** merges SSTables (a k-way merge keeping the newest version, dropping tombstones at the bottom).
  - _Leveled_ (LevelDB/RocksDB): levels ~10× bigger each, non-overlapping within a level → fewer files per read, more rewriting.
  - _Size-tiered_ (Cassandra): merge similar-sized files → cheaper writes, more files per read.

# Write amplification

`bytes physically written ÷ bytes the user wrote`. Sources: WAL write, memtable flush, and every time compaction **rewrites** the same data into a lower level (leveled ≈ 10× per level crossed). Trade-off triangle: **read / write / space amplification**.

# How a whole engine fits together (SQLite)

A SQL statement passes through layers, each with one job: the **tokenizer** and **parser** turn text into a tree; the **code generator** plans it as a small program of bytecode; the **virtual machine** runs that program, calling the **B-tree** module to read and write ordered keys; the **pager** caches fixed-size pages, handles the rollback journal or WAL, and locks the file; the **OS interface** does the actual reads, writes and `fsync`. Every database you meet repeats this stack, and the pieces you have built map onto it: your key-value store is a tiny B-tree-plus-pager, your WAL is the pager's journal.

# Bloom filter

A bit array of `m` bits and `k` hash functions. `Add`: set `k` bits. `MightContain`: all `k` bits set → **maybe**; any bit 0 → **definitely not**. **No false negatives**; false positives at rate ≈ `(1 − e^(−kn/m))^k`; with `m/n = 10` bits per key and `k ≈ 7` it is ~1%. Can't delete. It lets reads **skip SSTables** that don't contain the key.

```python
import hashlib

class Bloom:
    def __init__(self, m: int, k: int) -> None:
        self.m, self.k = m, k
        self.bits = bytearray((m + 7) // 8)

    def _positions(self, key: bytes):
        d = hashlib.blake2b(key, digest_size=16).digest()          # one hash, split into two
        h1 = int.from_bytes(d[:8], "little")
        h2 = int.from_bytes(d[8:], "little") | 1
        for i in range(self.k):
            yield (h1 + i * h2) % self.m                             # double hashing

    def add(self, key: bytes) -> None:
        for p in self._positions(key):
            self.bits[p >> 3] |= 1 << (p & 7)

    def might_contain(self, key: bytes) -> bool:
        return all(self.bits[p >> 3] >> (p & 7) & 1 for p in self._positions(key))
```

Do **not** use Python's built-in `hash()` for a filter you save to disk: string hashes are randomised per process (`PYTHONHASHSEED`), so the saved bits would mean nothing after a restart. Use a stable hash such as `hashlib` or `zlib.crc32`.

# Steps

1. **Memtable:** a `dict` + sort at flush time is the simplest (a sorted list with `bisect.insort` keeps it ordered); a skip list is the real thing. Track byte size; when `> threshold`, freeze it.
2. **Flush:** write sorted records `(klen, vlen, key, value)`; build the index (every Nth key → offset) and the Bloom filter; footer with offsets and a CRC. Write to a temp file, `os.fsync`, `os.replace`. Then truncate the WAL.
3. **Read path:** `memtable` → SSTables newest → oldest; stop at the first record (a tombstone means "not found"). Check the Bloom filter before touching a file.
4. **Delete** = write a tombstone to the memtable.
5. **Recovery:** list SSTables by sequence number; replay WAL into a fresh memtable.
6. (Stretch) merge two SSTables into one, keeping the newest value for each key.

# More conversions

- **Postfix → infix:** scan left→right; operand → push; operator → `b = pop(); a = pop(); push("(" + a + op + b + ")")`.
- **Prefix → postfix:** scan **right→left**; operand → push; operator → `a = pop(); b = pop(); push(a + b + op)`.
- **Postfix → prefix:** scan left→right; operator → `b = pop(); a = pop(); push(op + a + b)`.
- **Prefix → infix:** right→left, `a = pop(); b = pop(); push("(" + a + op + b + ")")`.
- **Infix → prefix/postfix:** shunting-yard (previous day).

Rule of thumb: the _evaluation order_ of stack pops reverses between left→right (postfix) and right→left (prefix) scans.

# Next greater element (monotonic stack)

For each element, the first larger value to its right, in O(n): keep a stack of candidates in **decreasing** order; scan **right to left**, pop smaller or equal elements, the top (if any) is the answer, then push.

```python
def next_greater(a: list[int]) -> list[int]:
    res = [-1] * len(a)
    st: list[int] = []
    for i in range(len(a) - 1, -1, -1):
        while st and st[-1] <= a[i]:
            st.pop()
        res[i] = st[-1] if st else -1
        st.append(a[i])
    return res
```

For "NGE I" (query values from `nums1` in `nums2`), build a dict `value → nge` over `nums2`. Circular variant: iterate `2n−1` indices.

Each element is pushed and popped once: **O(n)**.

# Measure with benchmarks, not intuition

Intuition about performance is wrong often enough to be dangerous: the Bloom filter may not help if misses are rare; the fsync may dominate everything.

1. Write a benchmark that matches the real workload (key sizes, read/write mix, hit/miss ratio).
2. Record a **baseline** (`pytest --benchmark-save=old`, or `timeit.repeat` results written to a file), change one thing, record the new run.
3. Compare: `pytest --benchmark-compare=0001` shows the difference with statistics; look at the spread, not one number.
4. Profile the hot path: `python3 -m cProfile -s cumtime`, or `py-spy` on a running process.
5. Keep the change only if the data supports it; write the numbers in the commit message.
