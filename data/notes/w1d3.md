# From source to instructions

Python source → compiler → **bytecode** (instructions for a stack machine, stored in a code object) → the interpreter loop, a big compiled function that fetches each bytecode and runs a piece of machine code for it. The CPU underneath still loops: **fetch → decode → execute**; the program counter (PC) points to the next instruction. Python adds a second, software fetch-decode-execute loop on top.

# arm64 (your Mac) cheat sheet

| Item                       | Meaning                                                           |
| -------------------------- | ----------------------------------------------------------------- |
| `x0`-`x30`                 | 64-bit general registers (`w0`.. = low 32 bits); `xzr` reads zero |
| `sp`, `pc`                 | stack pointer, program counter                                    |
| `x30` (LR)                 | link register: return address after `bl`                          |
| `ADD x0, x0, x1`           | x0 = x0 + x1 (dest first)                                         |
| `LDR x0, [x1, #8]` / `STR` | load / store from memory (only these touch memory)                |
| `CMP` + `B.LT`             | compare sets flags, conditional branch                            |
| `BL f` / `RET`             | call / return                                                     |

Load/store architecture: arithmetic works on registers only.

# Python's "assembly" is bytecode

The `dis` module prints the bytecode of any function. Each line is one instruction, and the operands are names, constants or jump targets, not registers.

```python
import dis

def add(a, b):
    return a + b

dis.dis(add)
# Python 3.12 (details differ a little between versions):
#   RESUME        0
#   LOAD_FAST     0 (a)
#   LOAD_FAST     1 (b)
#   BINARY_OP     0 (+)
#   RETURN_VALUE
```

`LOAD_FAST` pushes a local onto the value stack, `BINARY_OP` pops two values and pushes the result, `RETURN_VALUE` pops and returns it. The raw bytes are in `add.__code__.co_code`, the constants in `co_consts`, the local names in `co_varnames`.

```
python3 -m dis funcs.py              # disassemble a whole file
python3 -c "import dis, funcs; dis.dis(funcs.add, adaptive=True)"
```

# The adaptive interpreter

Since Python 3.11, a function that runs many times has its instructions **specialised** in place: `BINARY_OP` becomes something like `BINARY_OP_ADD_INT` once the interpreter has seen two ints, with a guard that falls back if the types change. `dis.dis(f, adaptive=True)` shows the specialised form after a warm-up. The output no longer mirrors the source one-to-one, much as optimised C stops mirroring it line by line.

# What a call costs

- Every bytecode is dozens of machine instructions inside the interpreter loop. `a + b` on ints is 4 bytecodes, but the work is a type check, a call into the int-add code, and an allocation for the result (unless it is a cached small int). In compiled machine code it is one `ADD`.
- **Method call:** `LOAD_ATTR` finds the function by looking at the instance and then the class and its bases (the MRO), and `CALL` runs it. After specialisation the lookup is cached, but it is still more than a direct `BL`. Dispatch is dynamic: nothing is known about the receiver's type until run time.
- **Bounds check:** `a[i]` runs `BINARY_SUBSCR`, which checks `i` against the length and raises `IndexError` if it is out of range.
- Python-to-Python calls reuse the interpreter's own stack frame since 3.11, so they are cheaper than they were, but they still build a frame.

```python
class Square:
    def __init__(self, s: float) -> None:
        self.s = s
    def area(self) -> float:
        return self.s * self.s

def f(shape) -> float:
    return shape.area()      # LOAD_ATTR (method) + CALL: found at run time
```

# Files and errors

```python
from pathlib import Path

try:
    with open("data.txt", encoding="utf-8") as f:
        for line in f:                  # one line at a time, not the whole file
            print(line.rstrip("\n"))
except FileNotFoundError:
    print("no such file")
else:
    print("read it all")                # runs only if nothing was raised
finally:
    print("always runs")
```

- Modes: `"r"` read (default), `"w"` truncate and write, `"a"` append, `"b"` bytes. Always pass `encoding="utf-8"` for text so behaviour does not depend on the machine.
- Catch the **specific** exception you can handle. A bare `except:` hides bugs, including `KeyboardInterrupt`. `raise` inside a handler re-raises the same error.
- `with` calls the object's cleanup (`__exit__`) even when the block fails, which is why it replaces manual `close()`.

# Classes and protocols (tutorial lesson 3)

A method is a function stored on a class; `self` is the explicit first argument. Python is **duck typed**: `f` above works for any object with an `area` method. `typing.Protocol` writes that expectation down for the type checker without any inheritance:

```python
from typing import Protocol

class Shape(Protocol):
    def area(self) -> float: ...
```

A class satisfies `Shape` just by having a matching method (no `implements`), as long as the signature fits.

# Linear scan patterns

One pass, keep running state in O(1) space: **O(n) time**.

```python
def largest(a: list[int]) -> int:           # assumes len(a) > 0
    m = a[0]
    for v in a[1:]:
        if v > m:
            m = v
    return m


def second_largest(a: list[int]) -> int:    # -1 if none distinct
    first = second = float("-inf")
    for v in a:
        if v > first:
            second, first = first, v
        elif first > v > second:
            second = v
    return -1 if second == float("-inf") else int(second)


def max_consecutive_ones(a: list[int]) -> int:
    best = run = 0
    for v in a:
        if v == 1:
            run += 1
            best = max(best, run)
        else:
            run = 0
    return best
```

Edge cases to test: empty input, one element, all equal, negatives, duplicates of the max (second largest must be _strictly_ smaller).

Linear search is `O(n)`; binary search needs sorted input and is `O(log n)`. `a[1:]` copies the list; use `itertools.islice` or an index if the extra copy matters.

# Let the toolchain check you

| Tool                    | Catches                                                                                        |
| ----------------------- | ---------------------------------------------------------------------------------------------- |
| `ruff format --check .` | formatting drift (so diffs show only real changes)                                             |
| `ruff check .`          | unused imports and variables, undefined names, risky patterns, many PEP 8 problems             |
| `mypy .`                | wrong types, once you add type hints (`None` where a value was expected, wrong argument types) |
| `pytest -W error`       | tests, with warnings turned into failures                                                      |
| `python3 -X dev`        | extra runtime checks: resource warnings, unawaited coroutines                                  |

Python will not tell you about an unused import or a misspelled attribute until that line runs, so these tools matter more than in a compiled language. Run them before every commit; later, in CI. Fix every finding rather than ignoring.

```
ruff format . && ruff check . && mypy . && pytest
```

1. **Adaptive interpreter.** After a function has run enough times, CPython rewrites its bytecode in place to specialised instructions guarded by type checks (for example `BINARY_OP_ADD_INT` when both operands have been ints). The result is faster, but it looks different from the plain listing and is tied to the types seen so far; if the types change, the guard fails and the instruction falls back. So the optimised bytecode may not mirror your source line by line.
2. **Cost of `a + b`.** In bytecode it is four instructions (`LOAD_FAST`, `LOAD_FAST`, `BINARY_OP`, `RETURN_VALUE`). Each one is a pass through the interpreter loop: fetch the opcode, jump to its handler, touch the value stack, and for the add, check both types, call the int-add routine and allocate (or reuse) a result object, plus reference-count updates. That is tens to hundreds of machine instructions where a compiler turns `a + b` into a single `ADD` in a register. This is why a tight Python loop is often 50 times slower than the same loop in compiled code, and why NumPy and other native libraries exist.
