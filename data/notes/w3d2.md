# Limited direct execution

Programs run **directly on the CPU** for speed; the OS keeps control with: (1) **user/kernel mode** and traps for privileged ops, (2) a **timer interrupt** that forces control back to the kernel periodically (preemption). The kernel then decides who runs next: the **scheduler**.

# Context switch

Save the outgoing thread's registers, PC and SP into its kernel/task struct, load the incoming one's, and if it's another process switch address space (page tables). **Direct cost:** hundreds of ns to a few µs. **Hidden cost:** the new thread finds cold caches, TLB and branch predictors, often dominating.

# Metrics

- **Turnaround** = completion − arrival. **Response** = first run − arrival. **Fairness** competes with both.

# Policies

| Policy      | Idea                                         | Strength                                        | Weakness                                             |
| ----------- | -------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------- |
| FIFO        | run to completion in arrival order           | simple                                          | **convoy effect**: short jobs wait behind a long one |
| SJF         | shortest job first                           | optimal avg turnaround (if all arrive together) | needs job lengths; starves long jobs                 |
| STCF        | preemptive SJF                               | good turnaround                                 | same                                                 |
| Round robin | time slice, rotate                           | best **response time**                          | poor turnaround; slice too small → switch overhead   |
| MLFQ        | multiple priority queues; learn job behavior | good both, no length knowledge                  | tuning, gaming                                       |

**MLFQ rules:** higher priority runs first; same priority → round robin; new jobs start at top; a job using its whole allotment is demoted; periodically **boost** everything to top (prevents starvation). Short/interactive jobs finish or block early and stay high, so it _approximates SJF without knowing lengths_.

# Python's three ways to run things at once

| Model                                           | What switches                                      | Cost to switch                                                    | Notes                                                                                                                                                                                                          |
| ----------------------------------------------- | -------------------------------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Threads** (`threading`)                       | real OS threads, scheduled by the kernel           | kernel context switch plus a hand-off of the GIL                  | only one thread runs Python bytecode at a time (the **GIL**); the interpreter asks the running thread to give it up every `sys.getswitchinterval()` (5 ms by default), and a thread blocked in I/O releases it |
| **asyncio tasks**                               | coroutines in one thread, switched only at `await` | a function return and call inside the event loop, no kernel entry | cooperative: one task that never awaits blocks all the others; the loop waits for I/O with `epoll`/`kqueue` through `selectors`                                                                                |
| **Processes** (`multiprocessing`, `subprocess`) | OS processes                                       | full kernel context switch plus a new address space               | each has its own interpreter and GIL, so CPU-bound work really runs in parallel                                                                                                                                |

Free-threaded builds of CPython (an optional build since 3.13) remove the GIL, at some cost in single-thread speed. Everything above still needs the OS for threads, blocking I/O, timers and memory.

```python
import asyncio, time

async def main(n: int = 100_000) -> None:
    ping, pong = asyncio.Queue(), asyncio.Queue()

    async def echo() -> None:
        while True:
            await pong.put(await ping.get())

    task = asyncio.create_task(echo())
    t0 = time.perf_counter()
    for _ in range(n):
        await ping.put(None)
        await pong.get()
    print((time.perf_counter() - t0) / (2 * n))    # about one task switch
    task.cancel()

asyncio.run(main())
```

The thread version uses two `queue.Queue`s and `threading.Thread`; the process version uses `os.pipe` pairs and a child started with `subprocess`.

# Simulator design

```python
from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class Job:
    id: int
    arrival: int
    burst: int

@dataclass(frozen=True)
class Result:
    id: int
    start: int
    finish: int

class Scheduler(Protocol):
    def run(self, jobs: list[Job]) -> list[Result]: ...   # FIFO, SJF, RoundRobin(quantum)
```

- Compute `turnaround = finish - arrival`, `response = start - arrival`; report averages per policy on the same workload (one long + several short jobs shows the convoy effect).
- RR gives the best average response; with a quantum of 1 it also maximizes context switches.

# Measuring switch cost

- Task ping-pong over two `asyncio.Queue`s (above); thread ping-pong over two `queue.Queue`s; then two processes (spawn yourself with `subprocess`) over `os.pipe` pairs.
- Expect tasks to be cheapest, threads dearer (they pay for the kernel and the GIL hand-off), processes dearest. Write down your own numbers rather than trusting any table.
- `taskset -c 0 python3 prog.py` pins to one core (Linux VM); `os.sched_setaffinity(0, {0})` does it from inside Python. Pinning two threads or two processes to one core often makes the ping-pong _faster_, because they share a core's cache and no cross-core wakeup is needed.

# Patterns

**Kadane's (max subarray sum), O(n):** best sum ending here = `max(v, cur+v)`.

```python
cur = best = a[0]
for v in a[1:]:
    cur = max(v, cur + v)
    best = max(best, cur)
```

(To also return the range, track the start index when you reset `cur = v`.)

**Next permutation, O(n):**

1. From the right, find the first `i` with `a[i] < a[i+1]` (none → reverse whole array).
2. From the right, find `j` with `a[j] > a[i]`; swap.
3. Reverse `a[i+1:]`.

**Majority element II (> n/3):** at most **two** candidates. Boyer-Moore with two candidates/counters, then a verification pass counting each.

**Repeating and missing in 1..n:** with `S = Σa − n(n+1)/2 = rep − miss` and `S2 = Σa² − Σi² = (rep−miss)(rep+miss)`, solve; or XOR trick; or mark visited by negating `a[|v|-1]`.

| Problem          | Time | Space |
| ---------------- | ---- | ----- |
| Kadane           | O(n) | O(1)  |
| Next permutation | O(n) | O(1)  |
| Majority II      | O(n) | O(1)  |

# Measure, then claim

A performance claim needs: **what** you measured, **how**, on **what machine**, with **what variance**.

- Warm up, repeat (`timeit.repeat(..., repeat=10)`), report median/spread with `statistics`, not one run. With pytest-benchmark, save runs and compare them.
- Change one variable at a time; control CPU frequency/background load; pin cores when relevant.
- Beware of measuring the wrong thing (imports, setup or printing inside the timed code), and of the first call being slower than later ones.
- Report units and the ratio, e.g. "task switch 4 µs ± 0.2 vs process 30 µs ± 3 (M2, Linux VM, one core)".
- Compare with known numbers as a sanity check.

1. **Context switch.** Saves/restores registers, PC, SP (and FP state), switches the page table/address space if the process differs, updates scheduler bookkeeping. Hidden cost: cold CPU caches, TLB misses, mispredicted branches for the newly running code.
2. **MLFQ ≈ SJF.** All jobs start at high priority. Short or interactive jobs finish or block before using up their allotment, so they stay high and run first, as SJF would. Long CPU-bound jobs use their allotment and sink. No prior knowledge of length is needed; behavior reveals it. Periodic boosts prevent starvation.
3. **Tasks vs threads.** An asyncio task switch happens in user space inside one thread: the coroutine returns to the event loop, which calls the next ready coroutine, with no mode switch and only a small frame to resume. A thread switch goes through the kernel and, in Python, a GIL hand-off. The event loop still needs the OS for the thread it runs on, for waiting on sockets and files (epoll/kqueue), for timers and for memory, and one blocking call stalls every task.
