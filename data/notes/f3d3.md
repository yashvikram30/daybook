# Three kinds of mistakes

| Kind                          | When it shows                                      | Example                         |
| ----------------------------- | -------------------------------------------------- | ------------------------------- |
| **Syntax error**              | before the program starts                          | missing colon or quote          |
| **Runtime error (exception)** | while it runs, and stops it                        | dividing by zero, a missing key |
| **Logic error**               | never: the program runs and gives the wrong answer | `<` where you meant `<=`        |

Logic errors are the hardest because nothing complains. The next sections give you the tools for the other two and a method for the third.

# Reading a traceback

```
Traceback (most recent call last):
  File "stats.py", line 9, in <module>
    print(average([]))
  File "stats.py", line 5, in average
    return sum(nums) / len(nums)
ZeroDivisionError: division by zero
```

Read it from the **bottom**: the last line is the error type and message; the line just above says where it happened; the lines above that are the chain of calls that got there. Common ones: `NameError` (a name that does not exist, often a typo), `TypeError` (wrong type, like `"a" + 1`), `ValueError` (right type, bad value, like `int("abc")`), `IndexError` (past the end of a list), `KeyError` (missing dictionary key), `FileNotFoundError`, `AttributeError` (that object has no such method), `ZeroDivisionError`.

# Handling errors with try and except

```python
def read_number():
    while True:
        text = input("Number: ")
        try:
            return float(text)
        except ValueError:
            print("That is not a number, try again.")
```

- Put in `try` only the code that might fail.
- Name the exception you expect. A bare `except:` hides real bugs, including your typos.
- `else:` runs if nothing failed; `finally:` always runs (good for cleanup).
- `raise ValueError("age must be positive")` signals a problem from your own function.
- Handle an error when you can do something sensible about it (ask again, use a default, print a clear message and exit). If you cannot, let it crash with its traceback, which tells you exactly what happened.

# Debugging as a method

1. **Reproduce** it with the smallest input that fails.
2. **Predict** what each step should produce.
3. **Look**: add `print(variable)` lines, or stop the program with the debugger.
4. **Narrow down**: find the first place where the actual value differs from your prediction. The bug is just before it.
5. **Fix one thing**, rerun, and keep the failing case as a test.

The debugger lets you pause and inspect. Put `breakpoint()` on a line and run: you get a `(Pdb)` prompt where `n` runs the next line, `s` steps into a function, `c` continues, `p x` prints a value, `l` lists the code around you and `q` quits. Explaining the code line by line to a rubber duck (or a friend) also works surprisingly often.
